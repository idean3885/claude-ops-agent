# 글 작성

마크다운 문서를 계획 → 초고 → 퇴고 순서로 쓰는 범용 엔진입니다.
문서 성격 파악, 시리즈 구조 설계, 작성 원칙 적용, 인라인 검증까지 포괄합니다.

> **플랫폼 발행은 이 스킬의 범위 밖입니다.** 오케스트레이터(사내 위키 발행 어댑터, `ops-agent:publish` 등)가 이 스킬을 호출하여 콘텐츠를 받고, 자체 발행 로직을 수행합니다.

## 금지 패턴 (HARD CONSTRAINTS)

| 금지 행위 | 이유 | 올바른 방법 |
|----------|------|------------|
| 리더빌리티·톤 자체 검증 | ops-agent:lint가 단일 소스, 자체 수행 시 기준 분산 | ops-agent:lint(inline) 위임 |

문장 단위 금지는 style-rules 가 원천입니다. 이유와 대체는 원천을 따르고 여기에 다시 적지 않습니다.

| 금지 행위 | 원천 |
|----------|------|
| 1인칭 · 주어 | → `config/style-rules/base/tone.md` T13 |
| 어미 혼용 | → `config/style-rules/base/readability.md` CJ2 |
| 감정어 · 수식어 | → `config/style-rules/base/ai-tells.md` D · F 계열 |
| em dash | → `config/style-rules/base/tone.md` T1 |
| 권위 용어 남발 | → `config/style-rules/base/tone.md` T11 |
| 짧은 부사절 뒤 관습적 쉼표 | → `config/style-rules/base/punctuation.md` PN1 |
| 세미콜론(`;`) | → `config/style-rules/base/punctuation.md` PN5 |

## 트리거

- "글 작성", "콘텐츠 작성", "블로그 초안", "write content"
- 단계 이름: "계획", "초고", "퇴고"
- 퇴고 점검 항목: "지면 활용"
- 기존 문서의 구조 변경 요청 (절 신설·항목 추가·시각 요소 변경 등)
- 다른 스킬에서 작성 위임 시 자동 호출

단계 어휘는 국어과 교육과정의 쓰기 과정을 그대로 씁니다. 계획 → 초고 → 퇴고 → 교정이고 교정 단계는 `ops-agent:lint` 가 담당합니다. 사용자가 스킬 이름을 외우지 않아도 단계 이름으로 도달합니다.

## 핵심 설계 원칙

### 원본 상세 → 목적별 가공

원본 콘텐츠는 상세할수록 좋습니다. 스펙, 대안, 트레이드오프, 수치, 출처까지 기록합니다.
발행 시점에 목적(블로그, 프레젠테이션 등)에 맞게 가공합니다.

> 수용하는 트레이드오프: 발행 시 변환 비용이 발생하지만, AI 자동화로 흡수.

### 단편 우선

→ `config/style-rules/extensions/blog.md` B6

### 시리즈 구조 (예외 케이스)

원천은 `extensions/blog.md` B3 이다. 아래는 작성 절차에 필요한 요약이다.

시리즈는 **인덱스(상위 문서)** + **개별 편(하위 문서)**으로 구성됩니다.

```
인덱스                     →    전체 파악 (30초 랜딩)
├── 1편                    →    독립된 문제→해결 스토리
├── 2편                    →    독립된 문제→해결 스토리
└── N편                    →    독립된 문제→해결 스토리
```

| 역할 | 인덱스 | 개별 편 |
|------|--------|---------|
| 목적 | 전체 구조 파악 | 특정 주제 깊이 |
| 독자 | 처음 방문자 (랜딩) | 관심 영역 독자 |
| 내용 | 개요 + 각 편 핵심 + 링크 | 완결된 문제→해결 스토리 |
| 갱신 | 편 추가/수정 시 | 개별 수정 |

### 개별 편 독립성

→ `config/style-rules/extensions/blog.md` B4

### 꾸준한 출력 시그널

→ `config/style-rules/extensions/blog.md` B5

## 절차

### Phase 1: 문서 성격 파악

콘텐츠 유형을 판별하여 이후 구조와 검증 기준을 결정합니다.

유형 목록과 유형별 익스텐션은 [config/style-rules/extensions/profiles.md](../../config/style-rules/extensions/profiles.md) 「2. 적용 대상」 을 따릅니다. 필수 구조는 판별한 유형 익스텐션의 「필수 구조」 절이 정본입니다.

자동 판별이 어려우면 사용자에게 확인합니다.

#### 착수 게이트 (GATE)

**신규 작성과 기존 문서 수정을 같게 봅니다.** 문장을 고치는 것과 무엇을 담을지 정하는 것은 다른 단계입니다. 후자를 건너뛰면 완성 후에 공백이 드러나 교정이 아니라 재작성이 됩니다.

규모로 강도를 나눕니다.

| 규모 | 게이트 |
|------|--------|
| 문장 한두 개 교정, 오탈자, 링크 | 면제 |
| 절 신설, 항목 추가·제거, 구조 변경, 시각 요소 추가·제거, 분량 재배분 | PU1·PU2 필수 |

전면 강제로 두지 않는 이유는 오탐 누적입니다. 오탈자 하나에 게이트가 뜨면 사람이 게이트를 끄게 됩니다.

유형을 판별한 뒤, 작성에 들어가기 전에 `config/style-rules/base/purpose.md` 의 PU1·PU2 를 적습니다.

| 계획 항목 | 적는 것 | 통과 조건 |
|-----------|--------|----------|
| PU1 | 이 문서가 답하는 질문 한 문장 | → purpose.md PU1 |
| PU2 | 독자가 가져갈 결론 목록 | purpose.md PU2 (셀 수 있고 각 항목이 형태를 갖는다) |
| 분량·시각 | 분량 하한·상한(행)과 시각 요소 개수 | purpose.md PU2 「분량 항목」 (두 수치가 실측에서 나온다) |

두 항목이 나오지 않으면 작성 단계로 넘어가지 않습니다. 사용자에게 이 문서가 무엇에 답하는지 확인하고, 조사를 더 하는 쪽으로 공백을 메우지 않습니다.

유형별 면제·완화는 `config/style-rules/extensions/profiles.md` 의 적용 강도 표를 따릅니다. 데일리로그처럼 기록 성격인 유형은 이 게이트를 건너뜁니다.

PU1 의 한 문장이 둘로 나뉘면 아래 단편/시리즈 결정에서 분리 후보로 넘깁니다.

#### 단편/시리즈 결정

단편 · 시리즈 결정은 `config/style-rules/extensions/blog.md` B6, 분할 단위와 별도 글의 조건은 같은 파일 B10 을 따릅니다. 시리즈 목록은 오케스트레이터가 제공합니다(예: wiki-tree.md, 블로그 카테고리 등). 새 시리즈 신설은 예외 케이스로 신중히 판단합니다.

### Phase 2: 내용 작성

사용자와 대화하며 내용을 작성합니다.

#### 실무자 위임

착수 게이트를 통과해 결정자가 승인한 계획이 있으면, 초고(Phase 2)와 퇴고(Phase 3-1)는 [agents/writing-operator.md](../../agents/writing-operator.md) 에 맡깁니다. 계획 게이트와 최종 확인은 결정자, 초고 · 퇴고는 실무자, 교정은 `ops-agent:lint` 입니다 ([ADR-0019](../../docs/adr/0019-roles-follow-raci-a-c-r.md)).

| 실무자에게 전달하는 것 | 담는 것 |
|------------------------|---------|
| 승인된 계획 | 착수 게이트의 PU1 한 문장, PU2 에서 승인한 결론 목록(개수와 각 결론의 내용), 분량 하한 · 상한, 시각 요소 |
| 문서 유형 | Phase 1 에서 profiles.md 로 판별한 유형 |
| 근거 자료 위치 | 근거가 필요한 문장이 참조할 자료 |

- 계획은 착수 게이트에서 결정자가 승인합니다. 실무자는 계획을 정하지 않으므로 게이트를 통과하지 않은 계획은 전달하지 않습니다. 게이트가 면제된 규모는 계획이 없으므로 위임하지 않습니다.
- 위임한 경우 3-3 교정도 실무자가 실행하고 반영 내역을 반환값에 싣습니다.
- 실무자의 반환값은 사용자에게 보이지 않습니다. 받은 즉시 사용자에게 전달하고, 전달 전에 다음 단계로 진행하지 않습니다.
- 실무자가 멈추는 조건으로 돌려준 항목은 결정자가 판정한 뒤 다시 맡깁니다. 그 자리를 대신 채워 쓰지 않습니다.
- 실무자의 완료는 통과가 아닙니다. 3-2 비평가 검토는 write 가 반환된 본문에 수행하고, 최종 확인은 write 를 부른 쪽(결정자)이 합니다.
- 위임하면 실행 순서는 실무자의 초고 · 퇴고 · 3-3 교정 → write 의 3-2 비평가 검토입니다. 3-2 에서 본문을 고치면 write 가 고친 부분만 `lint` 로 3-3 교정을 다시 실행합니다.

#### 공통 원칙

| 원칙 | 설명 |
|------|------|
| TL;DR | → readability.md V3 (유형별 면제는 profiles.md 「3. base 대비 적용 강도」) |
| 실무 사례 필수 | 이론만이 아닌 적용 맥락 포함 |
| 독립적 도입부 | → blog.md B4 |
| 말투 통일 | → readability.md CJ2 |
| 저자 톤 | 1인칭 · 주어는 → tone.md T13, 감정어 · 수식어는 → ai-tells.md D · F 계열. 개인 관점 표현 시 "~을 중요하게 생각합니다", "~라는 판단이었습니다" 등 간접 화법 사용. |
| 구두점 최소주의 | → punctuation.md PN1 · PN5 (한국어 구두점 전체는 PN1-PN8) |

#### 유형별 작성 가이드

**PoC**: 구조 · 요약 위치는 [poc.md](../../config/style-rules/extensions/poc.md) 가 정본. 코드와 실행 결과를 분리 배치 (코드 → 결과 → 해석).

**정보성**: 따라하기 용이성이 핵심. 각 섹션이 독립적으로 참조 가능해야 함.

**블로그 (PAAR 구조 필수)**: → `config/style-rules/extensions/blog.md` B1 (편 합치기는 B4)

### Phase 3: 퇴고 · 인라인 검증 (사전 verify)

작성 완료 후, 발행 전에 콘텐츠 품질을 확보합니다.
별도 verify 패스 없이 **작성 Phase에서 즉시 적용**합니다.

#### 3-1. 지면 활용

각 내용이 차지하는 지면이 그 가치에 맞는지 보고 배분을 고칩니다. 판정과 처방은 [readability.md V4](../../config/style-rules/base/readability.md) 가 정본입니다.

- 가치에 비해 넓은 내용을 줄이거나 지웁니다.
- 의도 없이 비거나 되풀이된 공간을 줄이거나 합칩니다.
- 핵심을 앞에 둡니다.

넓은 화면 문서(이슈 · 위키)에만 적용합니다. 모바일 독자가 있는 문서는 건너뜁니다.

#### 3-2. 비평가 검토

기준마다 통과 여부의 판정은 [experts/tech-comm.md](../../experts/tech-comm.md) 의 원칙(TC1~TC8)으로 내립니다. 아래 표는 검토 질문만 두고 판정 기준을 다시 적지 않습니다.

| 기준 | 검토 질문 |
|------|-----------|
| 주제 선명도 | 착수 게이트를 적용했으면, Phase 1 에 적은 PU1 문장이 완성본이 답하는 질문과 같은가. 게이트가 면제된 규모는 이 비교를 건너뛴다. 달라졌으면 어느 쪽이 맞는지 정하고 문서를 거기에 맞춘다 (판정은 TC1). |
| 톤 적합성 | → readability.md CJ2 · tone.md T13 · ai-tells.md D · F 계열 |
| 저자 관점 | 저자의 판단과 성장이 드러나는가 |
| 소재 활용 | 저자 고유 경험이 핵심을 구성하는가 |
| 대체 불가성 | → blog.md B7 「대체 불가성」 |
| 메시지 반복 | 같은 주장이 3회 이상 단순 반복되는가 (→ `length.md` 원인 판정 표 「주장 반복」 행) |
| 분량 적절성 | `base/length.md` LN1~LN2 적용 (총량, 채움 섹션, 밀도) |

#### 3-3. ops-agent:lint 위임: 리더빌리티 + 톤 검증 (GATE)

> **이 단계는 ops-agent:lint(inline)에 위임한다. ops-agent:write가 직접 검증하지 않는다.**

ops-agent:lint가 수행하는 검증 (ops-agent:write는 관여하지 않음):
1. 리더빌리티 적용 (콘텐츠 유형별 필수/권장 구분)
2. 저자 톤 검증 (→ `readability.md` CJ2 · `tone.md` T13 · `ai-tells.md` D · F)
3. 한국어 구두점 검증 (쉼표·콜론·세미콜론·종결 부호·물결표 규범, PN1-PN8)
4. 위반 항목 즉시 교정

ops-agent:lint(inline)는 교정된 본문을 반환합니다. 반환된 본문을 그대로 다음 Phase 로 넘깁니다.

### Phase 4: 메타데이터 프레임워크

콘텐츠에 발행 메타데이터를 부착합니다. 구체적 값(카테고리 목록, 태그 목록)은 오케스트레이터가 제공합니다.

```markdown
---

> **메타**
> 유형: {profiles.md 「2. 적용 대상」 의 문서 유형}
> 구성: {단편 | 시리즈 N편}
> 카테고리: {메인}, {서브}
> 태그: {태그1}, {태그2}, ...
> 발행: {드래프트 | 발행 | 보류}
```

## 하지 않는 것

- 플랫폼별 발행 (위키 API 호출, Jekyll 변환 등)
- pageId 매핑, 위키 트리 관리
- 대외비 제거 (퍼블리시 오케스트레이션의 역할)
- 스케줄 관리
