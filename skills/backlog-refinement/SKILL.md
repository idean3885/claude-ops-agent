# 이슈 정리

세션 마무리 때 넘긴 이슈가 쌓이면 같은 정리 순서를 손으로 반복하게 된다. 이 스킬은 그 순서를 고정한다. 사람의 판단 자리는 둘이다: 사람 판단 항목의 결론 · 플랜 컨펌과, 묶음 PR 의 머지 ([ADR-0040](../../docs/adr/0040-human-designs-and-decides-ai-ships-fast.md) 결정 1).

한 이슈의 생애주기(시작 · 커밋 · PR)는 flow 가 맡는다. 이 스킬은 여러 열린 이슈를 한꺼번에 판별해 무엇을 닫고 무엇을 묶을지 정하는 자리이고, 실행 단계는 flow 를 부른다.

## 입력원

판별 · 토론 · 보고 · 진행 단계는 입력원과 관계없이 같다. 다른 것은 1. 수집뿐이다. 입력원마다 스킬을 따로 두면 사람 판단 분류와 보고 형식을 두 곳이 정하게 되고, 언젠가 둘이 다르게 정한다.

| 입력원 | 1. 수집 | 언제 |
|--------|---------|------|
| 열린 이슈 | 열린 이슈 전부의 제목 · 본문 · 댓글 | 「이슈 정리」 요청 |
| 세션 발견 | 그 세션에서 나온 결함 · 사용자 교정 · 어시스턴트 판정 오류 · 미룬 잔여를 의뢰서 하나로 모은다. 항목마다 사실(무엇이 · 어디서 · 근거)만 적고 어시스턴트의 결론은 넣지 않는다 | 세션 마무리 |

세션 발견에는 두 규칙을 더한다.

- 어시스턴트 판정 오류(틀린 사실 · 틀린 절차 · 틀린 원인)는 원칙 토론에 올리지 않고 레슨런 게이트([learn](../learn/SKILL.md))로 보낸다. 같은 자리를 맡은 원칙이 이미 있으면 원칙을 더하지 않고, 그 원칙이 지켜지게 하는 장치(템플릿 · 테스트 · 지표)를 플랜에 넣는다. 오류를 낸 어시스턴트가 직접 판정하지 않는다. 판정은 맥락 없는 전문가가 한다.
- 5 의 컨펌은 플랜 승인이지 권한 부여가 아니다. 진행 중 막히는 권한(한시 권한 게이트 · 사람만 하는 쓰기)은 그 자리에서 다시 사람에게 넘긴다 ([ADR-0018](../../docs/adr/0018-gate-is-the-only-approval-channel.md)).

## 순서

| 단계 | 하는 일 | 멈춤 · 판정 |
|------|---------|-------------|
| 1. 수집 | 위 「입력원」대로 모은다. 판별은 fetch 뒤 원격 기준 브랜치의 워크트리(detached)에서 한다 ([docs/worktree.md](../../docs/worktree.md) 「적용 범위」). | 기준 커밋을 보고에 적을 수 있어야 한다. |
| 2. 판별 | 이슈마다 지금 main 의 코드 · 문서와 대조해 아래 「분류」 중 하나로 정한다. 「이미 반영」은 반영한 커밋을 찾은 뒤에만 쓴다. | 대조하지 않은 이슈를 분류하지 않는다. |
| 3. 바로 처리 | 「이미 반영」 · 「레포 밖」은 근거를 단 댓글과 함께 닫는다. 「판단 불필요」는 세션 묶음 하나로 고친다(flow, [ADR-0039](../../docs/adr/0039-session-bundle-one-commit-per-issue.md)). 「이슈 정리」 요청이 이 묶음의 착수 승인이다. | 수정 중 사람 판단이 필요한 결정이 나오면 그 이슈를 묶음에서 빼고 4 로 넘긴다. |
| 4. 토론 | 「사람 판단」과 조건이 찬 「대기」를 전문가 토론에 올린다(아래 「토론 의뢰」). | 결론 보고는 expert 스킬 「진행: 토론」과 보고 체크리스트를 따른다. |
| 5. 보고 · 컨펌 | 아래 「보고 형식」으로 결론과 플랜을 한 번에 내고 컨펌을 받는다. | 컨펌 전에는 4 의 결론을 실행하지 않는다. |
| 6. 진행 | 컨펌된 플랜을 세션 묶음으로 진행한다. 이 과정에서 나온 새 갭(토론 중 발견한 결함 · 새로 만든 이슈)도 같은 묶음에서 끝낸다. | 머지는 사람이 웹에서 한다. |
| 7. 마무리 | 머지 뒤 묶음의 이슈가 모두 닫혔는지 확인하고, 닫히지 않은 것은 근거를 달아 닫는다. 결과 한 줄을 남긴다(아래 「결과 기록」). | 열린 채 남는 이슈는 「대기」뿐이다. |

## 분류

| 분류 | 판정 기준 | 처리 |
|------|-----------|------|
| 이미 반영 | main 에 그 이슈의 완료 조건을 채운 커밋이 있다. | 커밋을 근거로 닫는다. |
| 레포 밖 | 결함 · 요구가 이 레포가 아닌 다른 도구 · 플러그인의 것이다. | 어디의 것인지 적고 닫는다(not planned). |
| 판단 불필요 | 고치는 방향이 이슈에 정해져 있고, 아래 「사람 판단」 범주에 걸리지 않는다. | 세션 묶음으로 바로 고친다. |
| 사람 판단 | 되돌릴 수 없는 행위 · 공개 표면(README 등) · 원칙 · ADR 신설과 번복 · 레포 경계 · 보안 ([ADR-0040](../../docs/adr/0040-human-designs-and-decides-ai-ships-fast.md) 결정 7). | 토론에 올린다. |
| 대기 | 이슈가 적은 조건(시범 기록 건수 · 다른 이슈 완료 · 사용자만 쓸 수 있는 원문)이 아직 차지 않았다. | 조건을 실측한다. 찼으면 「사람 판단」으로 옮긴다. 멈춘 채 목적이 다른 규칙으로 넘어갔으면 닫기를 추천한다. |

## 토론 의뢰

토론에 올릴 때는 공통 의뢰서 하나를 만들어 전문가마다 같은 것을 준다.

| 항목 | 내용 |
|------|------|
| 목적 | 사람의 주의를 쓸 가치가 있는 이슈만 남긴다. **냉정하고 비판적으로 본다.** 지금 레포가 같은 자리를 이미 맡고 있으면 닫기, 근거 없는 확장이면 기각을 말한다. |
| 기준 | 최근 변화를 담은 문서(최근 ADR · 작업 원칙 · 대화 발화 규칙 · 체인지로그 상단)를 먼저 읽고 지금 main 에 대조한다. |
| 배정 | 이슈마다 판정 기준이 걸리는 전문가만 배정한다(expert 「누구를 부르나」). 배정되지 않은 이슈에는 의견을 내지 않는다. |
| 출력 | 이슈마다 `판정(닫기 · 진행 · 고쳐서 진행 · 대기) \| 결론 한 문장 \| 근거 1~3줄(등급) \| 범위와 사람이 정할 것 \| 결론이 바뀌는 관측 조건`. |
| 반박 | 판정이 나뉜 쟁점만 상대 입장을 전해 한 차례 반박을 받는다. 반박 뒤에도 나뉘면 남은 이견으로 보고에 적는다. |

토론 중 범위 밖에서 발견한 결함은 넓히지 않고 사례 기록 이슈에 한 줄 남긴다. 사용자가 이번 묶음에서 끝내라고 하면 이슈로 만들어 6 에서 함께 고친다.

## 보고 형식

1. 첫 줄은 메시지 종류와 결론이다. 예: 「결정 요청 N건 · 닫음 N · 바로 고침 N」.
2. 사람 판단 항목은 이슈(번호 제목) · 결론 · 사람이 정할 것과 추천을 열로 둔 표 하나로 낸다.
3. 남은 이견은 쟁점마다 한 줄과 추천 이유.
4. 닫은 것과 바로 고친 것은 번호 제목만 한 줄씩. 근거 커밋은 요청받으면 낸다.
5. 마지막은 플랜(순서 목록)과 컨펌 요청 한 번이다. 다르게 할 항목만 답하면 되게 묻는다.

구현(파일 경로 · 코드 · 조회문)은 보고에 넣지 않는다. 실행 단계에서 낸다.

## 결과 기록

한 번 돌 때마다 마무리(7)에서 한 줄을 남긴다. 사용 횟수는 스킬 사용 지표가 자동으로 세지만, 정리가 잘 됐는지는 그 횟수로 알 수 없다.

```bash
python3 ~/.claude/ops-agent/current/scripts/backlog-log.py add --open-before <N> --closed <N> --bundled <N> --debated <N> --waiting <N> --reversed <사람이 추천을 뒤집은 수> [--note <한 줄>]
python3 ~/.claude/ops-agent/current/scripts/backlog-log.py report
```

닫은 뒤 다시 열린 이슈(거짓 닫기)는 다음 정리 때 2 에서 찾아 `--reopened` 로 남긴다.

## 하지 않는 것

- 대조하지 않고 오래됐다는 이유만으로 닫지 않는다. 닫을 때는 근거 커밋이나 결론을 단다.
- 사람 판단 항목을 컨펌 전에 실행하지 않는다.
- 토론 결론을 이슈마다 따로 묻지 않는다. 결론 보고와 플랜은 한 번에 낸다.
