# 기획 최신화

기획을 다시 읽어 지난번에 읽은 기획과 비교하고, 바뀐 항목이 설계의 어디를 바꾸는지 디프 드래프트로 적는다. 설계 · 기능 변경이 필요하면 드래프트를 본문으로 이슈를 올리고, 반영은 그 이슈에서 진행한다.

기획이 정답이다. 설계가 기획과 다르면 기본값은 기획대로 고치는 것이고, 회의로 가져갈 질문은 기획이 아직 정하지 않은 것뿐이다. 이 스킬은 그 대조를 한 번 하고 끝내지 않는다. 최신 기획(스냅샷)을 늘 유지해 두고, 바뀐 것만 다시 대조한다.

| 남는 것 | 휘발하는 것 |
|---------|-------------|
| 스냅샷 (최신 기획 원문과 지문) | 디프 드래프트 (이번 세션의 판단 재료) |
| 이슈 (설계 반영 이력) | |
| 진행 인덱스 (어디까지 언제 봤는가) | |

## 필요 시점

사용자가 부르지 않아도 아래 자리에서 돈다. 주기로 돌지 않는다. 기획이 필요 없는 세션은 비용이 0 이어야 한다.

두 자리 모두 그 프로젝트의 기획 오버레이가 있을 때만 돈다. 오버레이가 없으면 돌지 않고, 「오버레이」 절의 「파일이 없다」 동작도 하지 않는다.

| 자리 | 범위 |
|------|------|
| 이슈의 설계 · 구현을 시작할 때 | 그 이슈가 걸리는 도메인 |
| 화면 · 요구사항을 근거로 답하기 직전 (「기획에 없다」고 말하기, 사용자에게 화면 · 동작을 묻기) | 그 질문이 걸리는 도메인 |

1. 진행 인덱스에서 그 도메인의 항목을 찾는다. 스냅샷에 인덱스가 없으면 오버레이 출처에 적힌 범위로 먼저 만든다(상태 「추적」, 마지막 확인은 스냅샷의 마지막 갱신일).
2. 「범위 발견」을 돌린다. 추적 항목이 있어도 한다. 새 화면은 추적 중인 도메인의 다른 페이지에도 생긴다. 출처마다 세션에서 한 번이고 목록만 읽는다. 인덱스에 없다는 것은 기획에 없다는 뜻이 아니다.
3. 상태가 「추적」인 그 도메인 항목만 조회해 지문을 비교한다. 파일 전체를 다시 읽지 않는다.
4. 같은 세션에서 같은 도메인을 이미 확인했으면 다시 돌지 않는다.

조회 뒤의 디프 · 이슈 생성 판정 · 스냅샷 갱신(2~4 절)은 범위만 그 도메인으로 좁혀 그대로 따른다. 스냅샷 자체가 없으면 그 도메인 항목만 기준선으로 저장하고, 인덱스에서 그 도메인 항목의 마지막 확인만 오늘로 둔다. 사용자가 「기획 최신화」로 부르면 오버레이 출처에 적힌 범위 전체를 돈다.

## 역할

절차만 정한다. 판정과 반영은 이 스킬의 몫이 아니다 ([ADR 0019](../../docs/adr/0019-roles-follow-raci-a-c-r.md)).

| 무엇 | 누가 |
|------|------|
| 조회 · 디프 드래프트 · 이슈 생성 판정 | 이 스킬 (메인 세션이 직접. 조회는 도구 호출 몇 번이라 위임하지 않는다) |
| 이슈 상하위 구조 | 결정자가 그때 지시한다. |
| 항목마다 반영할지 판정 | 결정자 (이슈 안에서) |
| 새 기획 항목 자체가 타당한가 | 기획 전문가 ([`/expert`](../expert/SKILL.md), [`experts/planner.md`](../../experts/planner.md)) |
| 설계 원본 수정 | 소비 환경의 설계 문서 작성 절차 |

## 오버레이

기획 출처는 환경마다 다르다. 이 레포는 형태를 고정하지 않고, 소비 환경이 `~/.claude/ops-agent/planning/<프로젝트>.md` 에 선언한다. 파일 하나가 프로젝트 하나다.

| 항목 | 필수 | 담는 것 |
|------|------|---------|
| 출처 | 예 | 기획이 있는 곳(URL)과 읽을 범위. 화면 기획이면 페이지 · 프레임 단위로 적는다. 출처가 여럿이면 행을 나눠 모두 적는다. |
| 정본 | 예 | 출처 안에서 무엇이 정답인가 (예: 화면보다 프레임 주석) |
| 스냅샷 | 예 | 최신 기획을 저장하는 파일 하나. 아래 「진행 인덱스」 표를 같은 파일 머리에 둔다. |
| 설계 | 예 | 대조할 설계 원본의 위치 |
| 이슈 | 예 | 기획 반영 이슈를 올리는 곳과 절차 |
| 추출 | 아니오 | 정본 원문과 지문을 뽑는 스크립트 위치. 없으면 그 세션에서 읽고 원문을 손으로 나눈다. |
| 도구 | 아니오 | 조회 도구 오버라이드. 없으면 아래 기본값 |
| 판정 범위 | 아니오 | 설계 대조 · 이슈 판정을 하는 도메인. 없으면 전 도메인이다. 추적(스냅샷 최신화) 범위는 출처 전체이고 이 항목과 별개다. |
| 도메인 | 아니오 | 진행 인덱스의 도메인 열에 쓰는 낱말 목록. 이슈 · 질문을 도메인에 대응시킬 때 이 낱말만 쓴다. 없으면 인덱스를 처음 만들 때 결정자에게 받아 여기에 적는다. |

| 상황 | 동작 |
|------|------|
| 파일이 하나 | 그 프로젝트로 진행한다. |
| 파일이 여럿이고 지시에 프로젝트가 없다. | 어느 프로젝트인지 묻고 멈춘다. |
| 파일이 없다. | 출처를 묻고 멈춘다. 출처를 추측해 찾아 나서지 않는다. |

## 1. 조회

기본 도구는 Chrome DevTools MCP 다. 기획서 형태(화면 기획 · 문서 · 위키)를 가리지 않고 브라우저로 열 수 있으면 같은 경로로 읽는다. 오버레이에 `도구` 가 있으면 그것을 쓴다.

기본 도구로 조회하기 전에 `requires:` 를 확인한다. 미충족이면 [`bootstrap`](../bootstrap/SKILL.md) 의 미충족 보고를 내고 멈춘다. 오버레이의 `도구` 를 쓰면 이 의존은 쓰이지 않으므로 확인하지 않는다.

| 한다. | 하지 않는다. |
|------|-------------|
| 오버레이가 적은 범위(프레임 · 절)만 연다. 범위 발견은 목록만 읽는다. | 페이지 전체를 한 번에 읽는다. |
| 원문은 브라우저 안에서 모으고, 대화로는 지문부터 받는다. | 매번 원문 전체를 대화로 가져온다. |
| 스냅샷의 지문을 추출 쪽에 넘겨 비교하고, 바뀐 항목만 돌려받는다. | 비교하려고 스냅샷 원문 전체를 대화로 읽는다. |
| 화면은 바뀐 항목만 `take_screenshot` | 편집 · 코멘트 · 상태 변경 |
| 처음 허용받은 세션에서 필요한 권한만 쓴다. | 로그인 · 권한 요청을 대신 진행한다. |

로그인이 필요하면 에이전트가 기획 화면을 열어 둔 채 사용자에게 로그인만 요청하고 멈춘다. 로그인 뒤 이동 · 조회는 에이전트가 한다.

지문은 항목 하나의 정본 원문을 해시한 짧은 값이다. 원문이 한 글자라도 바뀌면 지문이 달라지므로, 지문만 비교해 바뀐 항목을 고른다. 지문 계산식은 스냅샷과 조회가 같아야 하므로 `추출` 스크립트 한 곳에 둔다.

### 진행 인덱스

스냅샷 머리의 표 하나다. 필요 시점에 「그 도메인을 언제 어디까지 봤는가」를 이 표만 읽고 판정한다.

| 열 | 담는 것 |
|----|---------|
| 출처 | 오버레이의 출처 행 (화면 기획이면 페이지) |
| 항목 | 프레임 · 절의 식별자와 이름 |
| 도메인 | 그 항목이 걸리는 업무 도메인 |
| 상태 | 추적 · 범위 밖 |
| 마지막 확인 | 추적은 지문을 비교했거나 기준선을 저장한 날짜(기준선이 아직 없으면 비워 둔다), 범위 밖은 결정자가 정한 날짜 |
| 사유 | 범위 밖이면 그 이유와 정한 결정자 |

기획이 원천이라 기획에 있는 항목은 추적이 기본이다. 「범위 밖」은 결정자가 빼라고 정한 것만 적는다. 범위 밖 행은 지우지 않는다. 지우면 다음 범위 발견이 같은 항목을 새 항목으로 다시 낸다.

추적은 스냅샷을 최신으로 두는 범위이고, 설계 대조 · 이슈 판정을 하는 판정 범위와 다르다. 판정 범위는 오버레이의 `판정 범위` 항목이 정한다.

### 범위 발견

필요 시점마다 출처당 세션에서 한 번 돈다. 출처의 항목 목록(화면 기획이면 페이지와 페이지의 최상위 프레임 이름)만 읽고, 인덱스에 없는 것을 새 항목으로 받는다. 본문은 읽지 않는다. 묻지 않는다.

| 결과 | 동작 |
|------|------|
| 새 항목이 그 도메인에 걸린다. | 인덱스에 추적으로 더하고 오버레이 출처에 적는다. 이번 조회에서 기준선을 저장한다. 보고에는 새 항목의 이름 · 위치를 한 줄로 붙인다. |
| 새 항목이 다른 도메인이다. | 인덱스에 추적으로 더하고 오버레이 출처에 적는다. 기준선은 그 도메인이 필요해질 때나 전체 실행 때 저장한다(마지막 확인을 비워 둔다). |
| 새 항목이 없다. | 「기획에 없음」으로 답할 수 있다. 확인한 출처를 함께 밝힌다. |

## 2. 디프

1. 추출 쪽이 스냅샷 지문과 비교해 돌려준 바뀐 항목(변경 · 추가 · 삭제)을 받는다. `추출` 이 없으면 이번 조회의 지문 목록을 스냅샷의 지문과 대화에서 비교한다. 같은 항목은 더 보지 않는다.
2. 지문이 다르거나 한쪽에만 있는 항목만 원문을 꺼내 스냅샷 원문과 행 단위로 비교한다. 「삭제」는 이번에 조회한 항목(프레임 · 절) 안에서만 판정한다. 조회하지 않은 범위의 스냅샷 항목은 비교하지 않고 그대로 둔다. 마지막 확인이 빈 추적 항목(기준선이 없는 새 항목)은 디프하지 않고 기준선으로 저장해 「기준선 생성 · 항목 N개」로 보고한다.
3. 결과를 디프 드래프트에 적는다.

| 분류 | 판정 |
|------|------|
| 추가 | 스냅샷에 없던 항목 |
| 삭제 | 이번에 없는 항목 |
| 변경 | 같은 항목의 정본 문구가 다르다. |
| 표현 변경 | 문구는 다르지만 뜻이 같다. 한 줄로 묶어 적고 대조하지 않는다. |

지문은 원문 글자만 본다. 원문에 담기지 않는 표시(취소선 · 글자색 같은 서식)만 바뀐 경우는 잡지 못한다. 그래서 증분은 기획을 믿는 전제에서 돌고, 증분이 틀어졌다고 볼 때(설계와 기획이 어긋난 자리가 디프 없이 나왔을 때 등)만 전체 원문을 다시 읽어 스냅샷을 새로 만든다.

스냅샷이 없으면 첫 실행이다. 디프 없이 이번 조회를 스냅샷으로 저장하고 「기준선 생성 · 항목 N개」만 보고한다. 기준선 전체를 설계와 대조하는 일은 범위가 다르므로 결정자가 따로 지시할 때 한다.

### 디프 드래프트

레포 밖 로컬 마크다운으로 쓴다 (기본 `~/.claude/ops-agent/planning-drafts/<프로젝트>-YYYY-MM-DD.md`). 판단 재료일 뿐이라 레포에 남기지 않는다. 짧으면 세션에 표로도 보인다.

추가 · 삭제 · 변경 항목마다 세 줄로 적는다.

```text
기획: <바뀐 정본 문구. 변경이면 스냅샷 → 이번>
설계: <설계 원본의 해당 자리와 지금 내용. 없으면 "설계 없음">
기획대로면: <설계 · 기능에서 바뀌는 것. 없으면 "변경 없음">
```

지어내지 않는다. 설계 쪽 대응 자리를 못 찾았으면 「설계 없음」으로 두고, 있을 것 같은 자리를 추측해 채우지 않는다. 기획이 정하지 않은 것은 「기획대로면」 대신 질문 한 줄로 적는다.

## 3. 이슈 생성 판정

기계적으로 정한다. 바뀔 때마다 이슈를 만들지 않기 위해서다. 오버레이 `판정 범위` 밖 도메인의 항목은 드래프트 · 이슈 판정 없이 스냅샷만 갱신한다.

| 드래프트 | 동작 |
|----------|------|
| 바뀐 항목 없음 · 표현 변경만 | 이슈를 만들지 않는다. 「변경 없음」 또는 표현 변경 한 줄로 보고한다. |
| 추가 · 삭제 · 변경이 있지만 모든 항목이 「기획대로면: 변경 없음」 | 이슈를 만들지 않는다. 드래프트 위치만 보고한다. |
| 「기획대로면」에 설계 · 기능 변경이 하나라도 있다. | 드래프트를 본문으로 오버레이 `이슈` 의 절차에 따라 이슈를 올린다. 상하위 구조는 결정자 지시를 따른다. |
| 기획 확인 질문이 있다. | 같은 이슈 본문에 미결로 적는다. |

반영(설계 원본 수정 → 구현)은 그 이슈에서 소비 환경의 절차로 진행한다. 이 스킬 안에서 설계를 고치지 않는다.

## 4. 스냅샷 갱신

디프와 별개로 스냅샷은 늘 최신이다. 이슈를 만들었든 아니든 이번 조회로 갱신한다.

1. 바뀐 항목의 원문과 지문을 스냅샷 파일에 덮어쓴다. 추가 항목은 더하고 삭제 항목은 지운다. 이전 상태는 레포 이력이 갖는다.
2. 항목마다 정본 원문을 요약 없이 남긴다. 요약하면 다음 지문 · 디프의 기준이 흐려진다.
3. 진행 인덱스에서 이번에 비교했거나 기준선을 저장한 항목의 「마지막 확인」을 오늘로 바꾼다. 범위 발견의 새 항목은 추적으로 더하고, 기준선을 미룬 항목은 마지막 확인을 비운다. 결정자가 뺀 항목은 「범위 밖」과 사유를 적는다.
4. 스냅샷이 레포 안이면 그 레포의 반영 절차(커밋 · 릴리스)를 따른다.

## 하지 않는 것

| 무엇 | 이유 |
|------|------|
| 기획 수정 · 코멘트 | 기획은 정답의 자리다. 읽기만 한다. |
| 디프를 레포에 남기기 | 디프는 판단용 임시본이다. 남는 것은 스냅샷과 이슈다. |
| 일정 · 진척 추적 | 기획 내용의 변화만 본다. |
| 주기 실행 · 세션 시작 자동 실행 | 기획이 필요 없는 세션에도 비용이 든다. 필요 시점에만 돈다 ([ADR-0036](../../docs/adr/0036-planning-sync-runs-at-point-of-need.md)). |
| 기획 문서 품질 판정 | 기획 전문가가 맡는다. |
