# Issue Skill

이슈 생애주기 관리 - 생성, 시작, 완료

## 트리거

- "이슈", "issue"

## Provider 참조

provider 파일에 인증 방식, API endpoint, request body 형식, 필드 보존 규칙이 정의되어 있다. API 호출 전에 읽고 그 정의를 따른다. 추측한 인증 헤더나 endpoint 로 호출하면 트래커마다 실패 양상이 달라 원인 추적이 어려워진다.

탐색 순서는 다음과 같다.

1. 로컬 provider: `~/.claude/ops-agent/providers/` 에서 현재 host와 매칭되는 `.md` 파일
2. 내장 provider: 플러그인 `providers/` 디렉토리
3. 기본값: `providers/github.md`

## 대외비 가드 (GATE 0)

이슈 관련 모든 텍스트(제목, 본문, 코멘트)는 공개 API로 전송되기 **직전** [../references/confidential-guard.md](../references/confidential-guard.md)의 검증 절차를 통과해야 한다.

검증 시점:
- `/issue create` 본문 작성 직후, API 호출 직전
- `/issue start` 시작 일시 코멘트 작성 직후, 기록 전
- `/issue complete` 결과 요약·완료 코멘트 작성 직후, 기록 전
- 모든 `gh issue edit` / `gh issue comment` 직전

히트 시 하드 차단하고 사용자에게 정정 요청. 훅(`scripts/pre-tool-use.mjs`)이 최종 방어선이지만, 가이드 단계에서 미리 키워드를 피해 작성하여 훅 단계까지 끌고 가지 않는다.

**규칙 소스**:

| 자리 | 담는 것 | 왜 거기인가 |
|------|---------|-------------|
| `~/.claude/ops-agent/confidential-keywords.local.json` | 키워드·패턴·internalHosts·allowPaths | 키워드는 감추려는 문자열 자체라 레포에 커밋하면 그 파일이 곧 유출이다 |
| 레포 루트 `.ops-agent/confidential.json` | `allowPaths` 만 | 어느 경로가 그 단어를 정당하게 다루는지는 머신이 아니라 레포의 성질이다. 로컬에만 두면 머신을 옮길 때 사라져 같은 커밋이 다시 막힌다 |

두 자리의 `allowPaths` 는 합쳐진다. 레포 파일의 키워드·패턴은 읽지 않는다.

## 레슨런 인덱스

이미 등재된 레슨런이 판단 시점에 읽히게 하는 절차다. 용어·파일 규약·재발 분석은 [../../../docs/lessons.md](../../../docs/lessons.md) 가 정본이고, 여기서는 **언제 읽고 무엇을 확인하는가**를 정한다. 아래 워크플로우가 이 절을 단계로 부른다.

### 로드 (세션 1회)

인덱스만 컨텍스트에 올리고 본문은 경로로 남긴다. 인덱스 한 줄은 `제목 · 어떤 판단에서 걸리는가 · 파일 경로` 셋을 담는다. 본문은 대조에서 걸린 항목만 연다. 자산이 늘어도 상주분은 한 줄씩 늘고, 여는 양은 걸린 항목 수를 따른다 (`config/style-rules/base/authoring.md` AU2·AU3).

1. 레슨런 버킷 경로를 확인한다. 소비 프로젝트의 규칙 문서가 선언한 경로를 쓴다 (PARA 배치면 `areas`)
2. 인덱스를 확보한다. 버킷에 인덱스 파일이 있으면 그것을 읽고, 없으면 버킷 안 레슨런 파일의 제목·상황 줄만 모아 인덱스로 쓴다. 이 단계에서 본문은 열지 않는다
3. 결과를 아래 네 문구 중 하나로 표시한다. 표시한 뒤에 다음 단계로 간다

| 결과 | 표시 문구 | 다음 |
|------|-----------|------|
| 인덱스 있음 | `레슨런 인덱스: N건 로드 (<버킷 경로>)` | 대조 지점에서 쓴다 |
| 버킷은 정의됐고 항목 0건 | `레슨런 인덱스: 0건 (<버킷 경로>)` | 그대로 진행 |
| 버킷 미정의 | `레슨런 인덱스: 버킷 미정의` | 그대로 진행. 새 위치를 만들지 않고, 어디에 둘지 사용자에게 물어 둔다 |
| 버킷은 정의됐고 인덱스를 읽지 못함 | `레슨런 인덱스: 로드 실패 <경로> (<사유>)` | 그대로 진행. 대조 지점에서 이 문구를 다시 적는다 |

**0건과 미정의는 다른 결과다.** 0건은 대조할 자산이 없다는 확인이고, 미정의는 자산이 있는지조차 확인되지 않았다는 뜻이다. 두 경우를 같은 문구로 적으면 하지 않은 확인이 한 것으로 남는다.

세션에서 이미 로드했으면 다시 읽지 않고 직전 표시 문구를 그대로 적는다.

### 대조 (판단 지점마다)

인덱스 전 항목을 훑어 지금 판단에 걸리는 항목을 선택하고, 걸린 항목의 본문을 열어 원천까지 확인한다. 확인 결과를 `대조 N건 / 걸림 M건` 형식으로 적는다. 걸림이 없으면 `걸림 0건` 이라고 적는다.

| 판단 지점 | 대조 대상 | 함께 확인하는 원천 |
|-----------|-----------|--------------------|
| 작업 단위를 정할 때 (`/issue create`) | 한 용건을 이슈 몇 건으로 두는가, 상위-하위를 어떻게 두는가 | 레포 규칙 문서의 해당 절을 직접 연다 |
| 브랜치를 만들 때 (`/issue start`) | 브랜치 접두·베이스·워크트리 여부 | provider 의 브랜치 패턴과 리모트 머지 이력에 남은 실제 접두를 조회한다 |

이 둘을 지점으로 삼은 근거는 되돌리는 비용이다. 여기서 정한 값은 뒤 단계가 전제로 깔고 가므로, 나중에 바로잡으려면 이슈나 브랜치를 다시 만들어야 한다. 커밋 메시지처럼 푸시 전에 고쳐지는 값은 지점으로 두지 않는다.

로드가 `버킷 미정의` 나 `로드 실패` 로 끝났으면 대조 자리에도 그 문구를 적고 진행한다. 대조하지 않았다는 사실이 기록에 남는다.

### 기존 수단 확인 (조건부)

**만들려는 것이 데이터·계정·환경일 때만** 수행한다. 그 밖의 작업에서는 건너뛰고, 건너뛴 사실을 적지 않는다. 조건이 없으면 모든 작업의 착수 부하가 늘고, 부하가 늘면 플로우를 우회하게 된다 (`base/authoring.md` AU2).

조건에 걸리면 애플리케이션 코드를 설계하기 전에 이미 그것을 만드는 수단이 있는지 본다.

| 볼 곳 | 어떻게 |
|-------|--------|
| 참조 사실 인덱스 | 「이 데이터는 무엇이 만드는가」가 이미 등재돼 있는지 |
| 운영 도구 | 다른 레포·스크립트가 같은 산출을 내는지 |
| 기존 테스트 자산 | 같은 데이터를 만드는 픽스처·시드가 있는지 |

**인덱스에 포인터가 있으면 따라간다.** 로컬 요약 인덱스는 세션 시작에 상주하지만 그 줄이 가리키는 외부 저장소는 명시 검색이 필요하다. 포인터를 보고 열지 않으면 저장돼 있어도 실패는 같다.

결과를 `기존 수단: 없음` 또는 `기존 수단: <무엇>` 으로 한 줄 적는다. 있으면 그것을 쓰는 안을 먼저 낸다.

## 서브커맨드

### `/issue create`

이슈를 생성한다.

**워크플로우**:
1. **레슨런 인덱스 로드**: 위 [레슨런 인덱스](#레슨런-인덱스) 의 로드 절차를 수행하고 결과 문구를 표시
2. provider 정의 파일 읽기
3. 이슈 제목 및 내용 파악 (사용자에게 질문)
4. **기존 수단 확인 (조건부)**: 만들려는 것이 데이터·계정·환경이면 [기존 수단 확인](#기존-수단-확인-조건부) 을 수행하고 결과를 한 줄 적는다. 아니면 건너뛴다
5. **작업 단위 결정 + 상위-하위 관계 체크**:
   - 한 용건을 이슈 몇 건으로 둘지 정하기 전에 [레슨런 인덱스 대조](#대조-판단-지점마다) 를 수행하고 `대조 N건 / 걸림 M건` 을 적는다
   - **분석과 구현을 별 이슈로 나누지 않는다.** 분석은 구현의 일부다. 나누면 분석 이슈가 결론 없이 닫히거나, 구현 이슈가 분석 결과를 다시 적는다
   - **고칠 층을 정한다.** 사상·규약 → 집행 → 개별 순으로 판정한다. 이슈 제목이 곧 층을 정하므로 여는 시점이 판정 시점이다. 규칙은 [../../../docs/adr/0004-fix-altitude.md](../../../docs/adr/0004-fix-altitude.md)
   - 상위 이슈가 존재하는지 확인 (사용자에게 질문 또는 컨텍스트에서 파악)
   - 상위 이슈가 있으면 `parentPostId`를 포함하여 하위 이슈로 생성
   - 기존 이슈 조회 시 상위 판단은 API 응답의 `parent` 객체 사용 (`parent.id`, `parent.number`, `parent.subject`)
   - 상위 이슈가 없으면 독립 이슈로 생성
6. **이슈 생성 게이트 (GATE 4)**: 제목·개수·상하위 구조를 표로 제시하고 승인을 기다린다. 표만 보이고 다음으로 넘어가지 않는다

   | 번호 | 제목 | 타입 | 상위 |
   |------|------|------|------|
   | 1 | … | feat | — |

   착수 지시(「이슈업하고 진행」)는 생성 승인이 아니다. 그 지시는 무엇을 할지에 대한 것이고, 이 게이트는 몇 건으로 어떤 구조로 만들지에 대한 것이다.

   **한 건이면 표 대신 한 줄로 제시한다.** 개수와 구조가 판단 대상인데 한 건에는 나눌 것이 없다. 표를 요구하면 게이트가 형식이 되고, 형식이 된 게이트는 읽히지 않는다

7. provider 정의에 따라 라벨/태그 매핑
8. 이슈 본문 작성 (provider의 본문 템플릿 사용)
9. **대외비 가드 (GATE 0)**: 제목·본문 전체에 대해 `references/confidential-guard.md` 검증. 히트 시 사용자 정정 후 재검증
10. provider의 이슈 생성 API/명령 실행 (provider에 정의된 인증·endpoint·body 그대로 사용)
11. **Extensions 실행**: provider에 post-create Extensions이 정의되어 있으면 실행

### `/issue start`

이슈 작업을 시작한다. 이슈 번호 또는 URL을 인자로 받는다.

**워크플로우**:
1. **레슨런 인덱스 로드**: 위 [레슨런 인덱스](#레슨런-인덱스) 의 로드 절차를 수행하고 결과 문구를 표시. 이 표시 없이 2번으로 넘어가지 않는다
2. provider 정의 파일 읽기
3. 이슈 식별 (번호, URL, 또는 사용자에게 질문)
4. provider의 상태 변경 API로 "진행 중" 전환 (provider의 dedicated API 사용)
5. 담당자 설정 (provider의 assignee 설정)
6. 시작 일시 텍스트 작성 (본문 추가용 또는 코멘트용)
7. **대외비 가드 (GATE 0)**: 위 6에서 생성된 텍스트에 대해 검증. 기존 필드를 수정하는 경우 새로 덧붙이는 텍스트만 검증 대상
8. provider API로 시작 일시 기록 (본문 추가 또는 코멘트, 기존 필드 보존)
9. **코드 작업 여부 확인**: "코드 작업이 필요한 이슈입니까?"
   - **Yes**: 브랜치명·베이스를 확정하기 전에 [레슨런 인덱스 대조](#대조-판단-지점마다) 를 수행하고 `대조 N건 / 걸림 M건` 을 적는다. 그다음 provider의 브랜치 패턴과 리모트 머지 이력에 남은 접두를 대조해 브랜치명을 정하고, `origin/{base}` 에서 분기한다
     - 워크트리 (권장): `git fetch origin && git worktree add ../{프로젝트}-{타입}-{번호} -b {브랜치명} origin/{base}`
     - 직접 체크아웃: `git fetch origin && git checkout -b {브랜치명} origin/{base}`
   - **No**: 브랜치 생성 스킵
10. **Extensions 실행**: provider에 post-start Extensions이 정의되어 있으면 실행

### `/issue complete`

이슈를 완료 처리한다. 이슈 번호 또는 URL을 인자로 받는다.

**워크플로우**:
1. provider 정의 파일 읽기
2. 이슈 식별 (번호, URL, 또는 사용자에게 질문)
3. 작업 결과 정리:
   - 사용자에게 작업 결과 요약 질문
   - provider의 완료 기록 형식에 따라 본문에 "작업 결과" 섹션 추가
4. 소요 시간 기록:
   - 시작 일시 ~ 현재 기준으로 실 작업 시간 계산
   - 점심(1h), 주말/공휴일 제외
   - 정수 올림, 일별 분배 형식 (예: `소요 시간: 8h (03/17 4h + 03/18 4h)`)
5. **대외비 가드 (GATE 0)**: 작업 결과 요약·소요 시간 코멘트 포함 모든 추가 텍스트 검증. 사용자 제공 요약이 핵심 방어 지점 (내부 용어 유입 가능성)
6. provider의 완료 상태 변경 API 실행 (provider의 dedicated API 사용)
7. 본문 업데이트 (provider의 PUT API, 기존 cc·태그·본문 보존 필수)
8. 브랜치가 있었으면 정리, 없었으면 스킵
9. workflow.json의 `currentIssues` 맵에서 현재 브랜치 항목 제거 (`del currentIssues[branch]`)
10. **Extensions 실행**: provider에 post-complete Extensions이 정의되어 있으면 실행
11. **자산 수집**: 이 이슈 기간의 교정 항목과 **조사로 확정한 참조 사실**을 함께 수집한다 ([../../../docs/lessons.md](../../../docs/lessons.md))
    - 참조 사실은 「무엇이 이 값을 만드는가」·「어느 경로가 정본인가」처럼 다시 조사하면 같은 답이 나오는 것이다. 조사에 비용이 들었으면 남긴다
    - 확인 날짜와 확인 방법을 함께 적는다. 참조 사실은 재발하는 것이 아니라 낡는다
    - 0건이면 아무것도 만들지 않는다
    - 기존 레슨런과 대조해 신규는 자산화하고, 재발은 분석으로 보낸다. 재발을 가드 추가로 처리하지 않는다
    - 시작 시 로드한 인덱스에 걸렸는데도 같은 오판이 났으면 재발로 잡고, 원인을 `docs/lessons.md` 의 원인 목록에서 선택한다
    - 수집 구현·버킷 경로는 소비 프로젝트가 정한다. 버킷이 미정의면 `레슨런 버킷 미정의` 로 표시하고 통과한다. 새 위치를 만들지 않는다

## Provider 연동 상세

이슈 생애주기의 구체적 동작은 provider에 위임한다:

| 위임 동작 | provider 참조 위치 |
|-----------|---------------------|
| 인증 헤더 | `Authentication` 섹션 |
| 이슈 생성 API | `Issue Lifecycle > create` |
| 라벨/태그 매핑 | `Issue Lifecycle > create > 라벨 매핑` |
| 본문 템플릿 | `Issue Lifecycle > create > 본문 템플릿` |
| 상태 변경 (dedicated API) | `Issue Lifecycle > start/complete > Workflow Change` |
| 본문 업데이트 (PUT) | `Issue Lifecycle > start/complete > Update` |
| 필드 보존 규칙 | `Known Bugs` 섹션 |
| 브랜치 패턴 | `Branch Pattern` 섹션 |
| 완료 기록 형식 | `Issue Lifecycle > complete > 결과 기록 형식` |
| 소요 시간 형식 | `Issue Lifecycle > complete > 소요 시간 기록 방법` |
| 기본 태그/CC | `Extensions` (있으면 적용) |
| post-action 확장 | `Extensions` (있으면 실행) |

## 규칙

- provider 파일을 읽고 API 를 호출한다
- **공개 표면으로 가는 모든 텍스트는 GATE 0 검증 후 송신** ([../references/confidential-guard.md](../references/confidential-guard.md))
- 레슨런 인덱스 로드는 결과 문구를 남긴다. 로드된 건수, 0건, 버킷 미정의, 로드 실패를 각각 다른 문구로 적는다
- 작업 단위와 브랜치명은 인덱스 대조 결과를 적은 뒤에 확정한다
- 이슈 생성/상태 변경은 사용자 승인 후에만
- 브랜치 생성은 코드 작업 이슈에서만 (사용자 확인)
- provider 정의에 라벨 자동 생성이 있으면 실행
- 완료 시 소요 시간은 정수 올림 (8h 초과 허용)
- 본문 업데이트 시 기존 cc, 태그, 본문 내용을 보존한다. PUT 은 전체 치환이라 누락분이 사라진다
