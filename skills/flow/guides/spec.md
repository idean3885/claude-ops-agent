# Spec Skill

명세(설계) 워크플로우

## 역할

요구사항을 분석하고 마크다운 명세 문서를 작성한다.

## 프로젝트 프로필 연동

`.claude/project-profile.md` 파일이 존재하면:
1. 프로필의 **`/spec 컨텍스트`** 섹션을 읽는다
2. 해당 컨텍스트에 정의된 설계 대상, 명세 항목, 다이어그램 방식을 따른다
3. 프로필이 없으면 아래 기본 워크플로우대로 동작한다

## 워크플로우

1. **프로필 확인**: `.claude/project-profile.md`를 읽어 프로젝트 특수성을 파악한다.
2. **요구사항 파악**: 사용자에게 질문하여 구현 대상을 명확히 한다.
3. **기존 문서 확인**: 프로젝트 내 관련 README, docs/ 문서를 읽어 컨텍스트를 파악한다.
4. **설계 문서 작성**:
   - 프로필이 있으면: 프로필의 `/spec 컨텍스트`에 정의된 항목 기준으로 작성
   - 프로필이 없으면 (기본값):
     - 아키텍처 설계 (Mermaid 다이어그램)
     - 인터페이스 정의 (입력/출력, API 스펙)
     - 구현 범위 및 제약사항
     - 규모 요구 (아래 「미확인 전제와 규모」)
5. **미확인 전제 판정**: 설계가 기대는 동작 중 아직 해보지 않은 것을 적고, 되돌리는 비용으로 PoC 대상을 가른다 (아래 「미확인 전제와 규모」).
6. **사용자 검토**: 문서를 제시하고 승인을 받는다. PoC 대상인데 결과가 없는 전제가 남아 있으면 승인 대상이 아니다.
7. **문서 저장**: 승인 시 `docs/` 또는 해당 모듈 README에 저장한다.

## 미확인 전제와 규모

설계가 맞아도 그 설계가 기대는 동작이 되는지는 해봐야 안다 ([ADR-0023](../../../docs/adr/0023-first-use-needs-observed-effect.md)). 설계 문서에 두 가지를 적는다.

**미확인 전제.** 처음 쓰는 외부 시스템 · 프레임워크 · 라이브러리의 동작 중 문서만 읽고 「된다」고 둔 것을 열거한다. 항목마다 틀렸을 때 되돌리는 비용으로 가른다.

| 틀리면 | 처리 |
|--------|------|
| 설계를 다시 해야 한다 (그 동작이 구조의 전제). | PoC 로 확인한다. 구조는 [poc.md](../../../config/style-rules/extensions/poc.md). 결과 링크 없이는 그 전제를 설계에 넣지 않는다. |
| 구현 안에서 바꿀 수 있다 (설정 · 옵션 · 세부 동작). | 구현 단계 실측으로 내린다. 설계에는 「구현에서 실측」이라고만 적는다. |

모든 새 도입에 PoC 를 걸지 않는다. 설정 한 줄에 문서가 붙으면 설계가 멈추고 절차를 우회하게 된다.

**규모 요구.** 동시성 · 응답 시간 · 데이터 양을 수치로 적는다. 구현 단계에서 「이 디테일이 필수인가 선택인가」는 이 수치와 대조해야 판정된다. 수치가 없으면 실무자는 기본값이 위반인지 알 수 없다.

## 산출물

- 설계 문서 (Markdown)
- 다이어그램 (Mermaid 임베딩, 상세 시 PlantUML + SVG)
- 미확인 전제 목록과 PoC 결과 링크 (PoC 대상이 있을 때)
- 프로필에 정의된 추가 산출물 (있는 경우)

## 규칙

- 코드 작성 금지 (설계만 수행). PoC 는 설계를 확정하기 위한 실험이라 예외, 결과 문서만 남김
- 구현 단계 실측이 설계의 전제를 깨고 돌아오면 설계 변경으로 접수. 구현에서 우회 금지
