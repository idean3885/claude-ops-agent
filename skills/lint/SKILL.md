# 교정

마크다운 문서를 규칙과 대조해 위반 위치를 찾습니다.

> **이 스킬은 리더빌리티 + 저자 톤 + 한국어 구두점의 단일 검증 소스입니다.**
> ops-agent:write(Phase 3, inline)와 ops-agent:publish(Phase 4, standalone)는 이 스킬에 위임합니다.
> 리더빌리티·톤 검증 기준을 변경할 때는 이 스킬만 수정합니다.

> **가독성 규칙 원천**: [config/style-rules/base/readability.md](../../config/style-rules/base/readability.md) (ops-agent SSOT, 미러: `~/.claude/ops-agent/style-rules/base/`)
> **AI 티 규칙 원천**: [config/style-rules/base/ai-tells.md](../../config/style-rules/base/ai-tells.md) (A~K 분류·심각도·품질 등급). 정량 지표는 [metrics/metrics-spec.md](../../config/style-rules/metrics/metrics-spec.md), 슬림 카운터는 [metrics/tells_count.py](../../config/style-rules/metrics/tells_count.py)

## 동작 모드

| 모드 | 호출 방식 | 용도 | 출력 |
|------|----------|------|------|
| **사후 (standalone)** | `/ops-agent:lint` 직접 호출 | 기존 글 다듬기, 소급 검증 | 리포트 + 교정 제안 |
| **사전 (inline)** | `ops-agent:write` Phase 3에서 자동 적용 | 작성 중 즉시 반영 | 규칙 위반 즉시 교정 |

### standalone 모드

독립 호출. 기존 콘텐츠를 검증하고 리포트를 생성합니다.
Phase 1~4 전체를 수행합니다.

### inline 모드

`ops-agent:write`가 작성 Phase에서 호출합니다.
가독성 + 비평가 기준을 작성 중 즉시 적용하여 별도 verify 패스를 제거합니다.
리포트 대신 **교정된 본문**을 반환합니다.

## 적용 범위

디렉토리 무관. 어떤 환경에서든 마크다운 콘텐츠를 검증합니다.

| 입력 | 처리 |
|------|------|
| 대화 중 작성된 본문 | 직접 검증 (가장 일반적) |
| 로컬 파일 경로 (`.md`) | Read 도구로 파일 읽기 |
| 없음 | 사용자에게 대상 질문 |

> 위키 URL/페이지 ID로 원격 콘텐츠를 조회하는 것은 이 스킬의 범위 밖입니다.
> 원격 콘텐츠 검증이 필요하면 오케스트레이터가 콘텐츠를 조회한 뒤 이 스킬에 본문을 전달합니다.

## 동작 흐름 (standalone)

### Phase 1: 대상 파악 + 유형 판별

1. 검증 대상 콘텐츠를 수집합니다
2. [config/style-rules/base/readability.md 콘텐츠 유형별 프로필](../../config/style-rules/base/readability.md)에 따라 유형을 판별합니다

| 콘텐츠 유형 | 판별 조건 |
|-------------|----------|
| PoC | 기술 검증 목적, 코드 비중 높음, 결론이 "된다/안 된다" |
| 정보성 | 개념 설명/절차 안내, 독자가 따라할 수 있는 구조 |
| 시리즈 어필 | 프로젝트 경험 기록, 포트폴리오용, 저자 판단이 핵심 |
| 지식 | 개발 사전/노하우, 기억용 간결체 (요약 면제) |
| 장표 | 비교·판단 전달이 목적. 표가 본체이고 산문이 표를 잇는다. 읽는 문서가 아니라 훑는 문서 |

자동 판별이 어려우면 사용자에게 확인합니다.

### 읽는 쪽 판정 (유형 판별과 별개)

유형은 사람이 읽는 문서의 성격을 나눕니다. 그것과 별도로 **읽는 쪽이 모델인지**를 봅니다. 아래에 해당하면 `authoring`(AU1~AU6) 규칙을 추가로 적용합니다.

| 문서 갈래 | 해당 파일 |
|-----------|-----------|
| 스킬 문서 | `SKILL.md`, `skills/**` 의 가이드·참조 문서 |
| 레포 지침 | `CLAUDE.md`, `AGENTS.md` |
| 정의 문서 | `providers/*.md`, `agents/*.md` |

한 파일이 두 쪽 다 읽는 경우가 있습니다. `SKILL.md` 는 모델이 실행하고 사람이 훑습니다. 그때는 **읽는 쪽을 기준으로 `authoring` 이 이깁니다.** 사람 가독성 규칙이 요구하는 형식과 `authoring` 이 요구하는 것이 부딪히면, 그 문서가 존재하는 이유는 모델이 실행하는 것이므로 실행 쪽을 지킵니다.

### 목적 대조 (Phase 2 선행)

네 검사에 들어가기 전에 [config/style-rules/base/purpose.md](../../config/style-rules/base/purpose.md) 의 PU1·PU2·PU5 를 대조합니다. 표현·구조 교정보다 먼저 하는 이유는, 전제와 어긋나 통째로 빠질 절을 먼저 다듬으면 그 교정이 버려지기 때문입니다.

| 규칙 | 대조할 것 |
|------|-----------|
| PU1 | 이 문서가 답하는 질문을 완성본에서 한 문장으로 추출할 수 있는가. 추출한 문장이 제목·도입부가 말하는 것과 같은가 |
| PU2 | 독자가 가져갈 결론을 세어 목록으로 적을 수 있는가 |
| PU5 | 문서가 세운 전제와 문서의 구성 방식이 어긋나는 쌍이 있는가 |

PU5 대조는 사실 정확성 검사의 문장 단위 인과 검사와 다릅니다. 문장이 각각 참이어도 문서 전체가 자기 전제를 배반할 수 있습니다. 전제를 명시한 문장을 먼저 모으고, 각 전제가 문서의 절 구성·측정 단위·비중 배분과 어긋나지 않는지 하나씩 봅니다.

여기서 걸리면 결과는 문장 교정이 아니라 **구조 처방**입니다. 어긋난 쌍을 리포트에 적고, 전제와 구성 중 어느 쪽을 고칠지는 저자가 정합니다.

유형별 면제·완화는 [config/style-rules/extensions/profiles.md](../../config/style-rules/extensions/profiles.md) 의 적용 강도 표를 따릅니다.

#### 1. 사실 정확성

> "기술적 주장이 정확한가? 원문에서 윤문된 경우 의미가 보존되는가?"

##### 1-A. 기술적 정확성

- 기술 용어가 정확하게 사용되는가?
- 코드 예시가 실제 동작과 일치하는가?
- 수치, 버전, 설정값이 정확한가?
- 인과관계 설명이 논리적으로 타당한가?
- 출처가 필요한 주장에 근거가 있는가?

##### 1-B. 의미 보존 13항 (윤문·교정 시 필수)

원문에서 윤문되었거나 외부 AI 글을 가져와 가공한 경우, 아래 13항을 항목별로 검증한다.
출처: [`epoko77-ai/im-not-ai`](https://github.com/epoko77-ai/im-not-ai) 의 `content-fidelity-auditor` (MIT 차용).

| # | 보존 대상 | 검증 질문 |
|---|-----------|----------|
| 1 | 고유명사 | 인명·지명·제품명·모델명·기관명이 한 글자도 다르지 않은가 |
| 2 | 수치·단위 | 숫자·백분율·연도·금액·단위가 동일한가 |
| 3 | 날짜·시간 | 연·월·일·시·기간이 동일한가 |
| 4 | 직접 인용 | 큰따옴표 안 내용이 원문과 100% 일치하는가 |
| 5 | 법률·규정 조문 | 조·항·호 번호 및 본문이 그대로인가 |
| 6 | 수식·공식 | 수학·화학·통계 표기가 보존되는가 |
| 7 | 주장·결론 방향 | 긍정 → 부정·단정 → 추측 등 방향 전환이 없는가 |
| 8 | 인과관계 | A → B 가 B → A 로 뒤바뀌지 않았는가 |
| 9 | 주어 변경 시 의미 유지 | 피동 → 능동 전환이 행위자를 바꾸지 않았는가 |
| 10 | 양화·한정 | "모든·대부분·일부" 의 강도가 유지되는가 |
| 11 | 긍정·부정 극성 | 이중 부정 단순화 시 극성이 뒤집히지 않았는가 |
| 12 | 순서 | 열거의 순서가 의미를 담은 경우 보존되는가 |
| 13 | 누락·첨가 | 원문 정보를 삭제하거나 없는 정보를 추가하지 않았는가 |

처음 작성된 글(원문 비교 대상이 없는 신규 글)은 1-A 만 적용. 1-B 는 윤문·교정·외부 글 가공 시점에 적용.

#### 2. 구조와 완성도

> "읽는 사람이 오해 없이 끝까지 읽을 수 있는가?"

검증 포인트:
- TL;DR이 본문 핵심을 정확히 요약하는가?
- 도입부가 독립적으로 읽히는가?
- 논리 흐름이 자연스러운가? (문제→원인→해결→결과)
- 결론이 도입부의 약속을 이행하는가?
- 인용·참조가 `목적 대조` 에서 뽑은 PU1 질문에 답하는가? 방법 선택만 방어하고 목적에 답하지 않는 근거가 늘어나 있으면 `purpose.md` PU4
- 유형별 필수 구조를 갖추었는가? (readability.md 콘텐츠 유형별 프로필 참조)
- 합쇼체로 통일되었는가? ("~다/~이다" 혼용 없음)
- "저는/나는" 없이 주어 생략 서술인가?
- 감정어·수식어가 최소화되었는가?
- 저자 톤 T1~T23을 위반하지 않는가? (tone.md 참조: em dash, 도치, 체언 종결, 도입부 메타 중복, 즉석 명명, 영어 용어 괄호 풀이, 기계적 수치 강조체, 구어체 동사, 임의 신조어 합성, 수학·논리 기호 남용, 권위 용어 남발, 분석 틀 라벨 헤딩 노출, 1인칭 회상 통일, 방어적·변명조 프레이밍, 메타 어필 직접 노출, 개념 병렬 `+` 기호 남용, 어휘 고정, 제목의 내용 지목, 수량 숫자 표기, 이유 문장 분리, 자료 도입 어법, 고유명사 정식 표기, 정착한 외래어의 순화어 치환)
- **문장이 한 번에 읽히는가** (`readability.md P10·P11`): 지시어가 가리킬 대상이 앞에 실물로 있는가. 소리 내어 읽었을 때 되돌아가는 문장이 있는가. 구조가 맞아도 이 층에서 독자가 멈춘다
  - 블로그·평가자 지향 매체는 T15의 본문 어필 어휘를 `extensions/blog.md B9` 기준으로 검출한다 (면접·시니어·포트폴리오·이력서·채용 등이 본문 프로즈에 등장하는가)
- 한국어 구두점 PN1~PN6를 위반하지 않는가? (punctuation.md 참조: 짧은 부사절 뒤 쉼표, 연결어미 `-고` 뒤 쉼표, 열거 접속어 앞 쉼표, 콜론 오용, 세미콜론, 가운뎃점 병렬·슬래시 지양)

#### 3. 독립 가치

> "이 글 하나만 읽어도 가치가 있는가?"

검증 포인트:
- 시리즈의 다른 편을 읽지 않아도 이 글이 성립하는가?
- 하나의 문제→해결 스토리가 완결되는가?
- 독자가 이 글에서 하나 이상의 실무 인사이트를 얻는가?
- 제목이 글의 핵심 가치를 드러내는가?
- 서로 다른 문제(다른 검색 의도)를 한 글에 함께 담아 초점이 흩어지지 않는가? (그렇다면 문제별 독립 글로 분리 제안: `extensions/blog.md` B10)
- 반대로, 단독 성립·서사 완결이 안 되는 얕은 조각을 별도 글로 분리하지 않았는가? (그렇다면 흡수 제안: B10 품질 게이트)

#### 4. 가독성 + AI 티

> "마크다운 형식이 독자의 스캔/이해를 돕는가? AI 가 쓴 흔적이 남아 있지 않은가?"

[config/style-rules/base/readability.md § 검증 체크리스트](../../config/style-rules/base/readability.md)의 규칙 전체를 적용합니다.
콘텐츠 유형 프로필에 따라 `●`(필수) 위반은 보고하고, `○`(권장) 위반은 제안으로 분류합니다.

가독성 검증 순서:
1. 헤딩 계층 (H1-H4)
2. 문단 구조 (P1-P12)
3. 목록/테이블 (L1-L5). L5 는 비교표 뒤에 그 비교의 결론이 있는지 본다
4. 코드/기술 요소 (C1-C3)
5. 시각적 리듬 (V1-V3)
6. CJK 특화 (CJ1-CJ3)
7. Blockquote 렌더링 (BQ1)
8. 저자 톤 (T1-T23)
9. 한국어 구두점 (PN1-PN6)
10. 문서의 목적 (PU6 근거 확인 상태): [base/purpose.md](../../config/style-rules/base/purpose.md)
11. 산출물 분량 (LN1-LN2): [base/length.md](../../config/style-rules/base/length.md)
12. 다이어그램 라벨: 소스 펜스(`plantuml`·`mermaid`)의 라벨 문자열만 추출해 본문과 따로 검증한다. 대상은 T17(어휘 고정)·T8·K-4(물리 조작 동사)·T22(고유명사)이고 근거는 [extensions/architecture.md](../../config/style-rules/extensions/architecture.md) AR8. 아키텍처 문서가 아닌 산출물(이슈 본문·위키 등)에 들어간 다이어그램도 대상이다
13. 에이전트가 읽는 문서 (AU1-AU8): [base/authoring.md](../../config/style-rules/base/authoring.md). 위 "읽는 쪽 판정" 에 걸릴 때만 적용

LN 은 마지막에 적용한다. 톤·AI 티 교정으로 살아나는 섹션을 먼저 삭제하지 않기 위해서다.
총량 측정은 위반 항목이 아니라 LN1·LN2 를 언제 적용할지 정하는 절차다. 기준값 표본이 3편 미만이면 총량 판정을 건너뛴다.
LN1(채움 섹션)은 필수(●), LN2(밀도)는 권장(○). 밀도가 높아 분량이 큰 경우는 교정 대상이 아니다.

AI 티 검증 ([ai-tells.md](../../config/style-rules/base/ai-tells.md) A~K):
1. A~K 패턴을 span 단위로 탐지하고 S1/S2/S3 로 분류한다
2. S1 건수와 S2 빈도를 집계한다. **정확도 우선** 요청 시 `python3 config/style-rules/metrics/tells_count.py <파일>` 로 이중피동·이중조사·대명사밀도·light verb·연결어미 쉼표·대칭 대구(C-10)·em dash(T1)를 객관 수치로 확보해 눈대중 카운트를 대체한다
   - `em_dash_count` 는 합격선 0 이다. T1 에 위치 조건이 없으므로 산문뿐 아니라 목록 항목 구분자·표 셀·인용에 쓰인 것도 위반이다. 눈으로 훑으면 참고 링크 목록의 구분자 자리가 잘 남는다. 대체는 괄호·쉼표·줄바꿈
3. S1 0건·S2 ≤2건 → 등급 A, S1 0건·S2 ≤4건 → B, S1 1~2건 → C, S1 3건+ → D (ai-tells.md 기준 재사용)
4. C-10 대칭 대구는 정규식 오탐이 있을 수 있으므로 카운트를 참고치로 보고 문맥으로 최종 판정한다
5. **등록 패턴 대조로 끝내지 않는다**: 등록 목록은 오탐이 낮은 것만 담으므로 같은 계열의 다른 표현을 놓친다. 목록에 없어도 원칙으로 판정한다
   - K-4 / `tone.md` T8(물리 조작 동사): 추상 대상(도구·로직·규칙) + 물리 조작·파괴 어근 + 행위 어휘 쌍 파괴 → 순화. 도메인 정합 은유·확립된 관용구·IT 표준 한국어는 예외
   - **`physical_verb_count` 0 을 통과로 읽지 않는다.** 그 값은 등록 목록 안만 본다. 실측에서 12건 중 3건만 등록 경로에 걸렸고 나머지는 위 3조건으로 잡혔다
   - K-2·K-3(의인화·구어 감정체): 시스템·서비스를 사람처럼 서술하면 등록 여부와 무관하게 도메인 동사로 교체
   - `tone.md` T22(고유명사 축약·추상화): 문서에 등장한 제품명·조직명·시스템명 목록을 만들고, 그 부분 문자열이 선언 없이 단독으로 쓰인 자리를 찾는다. 상위 개념으로 바꾼 자리는 선언이 있어도 위반
   - `tone.md` T23(정착한 외래어의 순화어 치환): 다이어그램 · 태그 · 캡처처럼 외래어가 표준인 개념을 한자어 · 고유어로 바꾼 자리를 찾는다. 판정 기준은 독자 코퍼스이고, 등록 목록(도식)에 없어도 정착 표기로 교체한다
   - F-6(같은 명사 반복): 한 문장에 같은 명사가 두 번 나오면 두 번째가 가리키는 대상을 본다. 같은 대상이면 지시어·접속어·생략으로 지우고, 다른 대상이면 나란한 것은 가운뎃점으로 통합하고 대조하는 것만 남긴다
   - F-8(한자 접두 조어): `未`·`非`·`無`·`不` 가 명사에 붙은 낱말을 골라 사전·독자 코퍼스에 있는지 본다. `미결`·`미정`·`비활성` 은 통과, `미인지`·`미보관`·`비기재` 는 `알 수 없음`·`~하지 않는다` 로 풀어 쓴다. 개조식 표 셀에서 주로 생긴다
   - T20(이유를 별 문장으로 뗌): `A 입니다. B 이기 때문입니다.` 형태를 붙였을 때 뜻이 달라지는지 본다. 달라지지 않으면 한 문장으로 붙인다
   - T12(방법론 라벨): 헤딩뿐 아니라 본문·캡션·괄호의 틀 이름도 지운다
   - L6(표·목록 되풀이): 표 앞뒤 산문을 지웠을 때 표에 없는 정보가 사라지는지 본다. 사라지지 않으면 지운다
   - G 계열·D-17(완곡과 과장): 완곡을 표현의 양으로 판정하지 않는다. 그 문장이 근거를 대는지 본다. 근거가 확실한데 완곡하면 회피다. 근거가 불확실한데 단언하면 과장이다. **완곡을 단언으로 바꾸는 교정은 하지 않는다.** 회피를 과장으로 옮기는 것이다. `absolutist_count` 가 그 결과를 재지만 절대치로 판정하지 않는다. 전수를 확인한 문장의 `모든` 은 정확한 표현이다
   - 목록 미등록 표현을 걸렀다면 어떤 원칙으로 판정했는지 리포트에 한 줄로 남긴다

### Phase 4: 교정 (선택)

사용자가 교정을 요청하면:
1. 필수 위반 항목만 자동 교정 (권장은 제안만)
2. 교정 전후 diff를 보여주고 확인 후 적용
3. 로컬 파일: 직접 수정

**과윤문 게이트 (4대 철칙 #4 실측)**: 교정 후 `python3 config/style-rules/metrics/tells_count.py --before <원문> --after <교정본>` 으로 변경률을 측정한다. `<원문>`·`<교정본>` 은 텍스트를 그대로 넘겨도 되고 파일 경로여도 된다(경로가 실재하면 파일, 아니면 리터럴로 취급). `warn`(30% 초과)이면 사용자에게 경고, `abort`(50% 초과)이면 교정을 중단하고 원문 의미 훼손 여부를 사람이 검토한다. inline 모드(write Phase 3)는 이 스크립트 게이트를 호출하지 않는다(핫패스 비용 회피, 기존 체크리스트 자가 검증만).
