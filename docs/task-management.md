# 이슈 관리 전략

이슈를 어떤 크기로 잡고 어떻게 진행 · 리뷰 · 배포하는지 정한다. 특정 조직의 특수가 아니라 업무 진행 전체에 쓰는 전략이다. 이슈 가이드(`skills/flow/guides/issue.md` 「이슈 단위 결정」)는 이 문서를 따른다.

목표는 이슈 관리 비용을 낮추면서 진행을 보이게 하는 것이다. 이슈는 주간 보고에 올릴 수 있는 크기로 잡는다.

## 규칙

| # | 규칙 | 뜻 |
|---|------|----|
| 1 | 이슈 크기는 루틴 여부로 정한다. | 루틴한 작업(버그 수정 · 정해진 절차 · 예측되는 변경)은 하루 안에 끝내는 크기로 잡고, 넘기면 사유를 묻는다. 루틴하지 않은 작업(진행하며 요구 · 계약이 바뀌는 설계 · 신규 기능)은 What · Why 가 분명하면 이슈 하나를 며칠 끌어도 된다. |
| 2 | 이슈 하나는 PR 하나다. | 피처 단위 전체를 한 PR 로 끝낸다. 코드 분량은 나누는 기준이 아니다 ([ADR-0032](adr/0032-one-issue-one-pr-review-design-not-code.md)). |
| 3 | Todo 는 PR 안의 진행 단위다. | 진행 중 걸리는 것은 그 이슈의 Todo 체크리스트에 더한다. 보고(스크럼 · 일일 계획)에는 지금 어느 Todo 인지 적어 진행을 보인다. |
| 4 | 파생 건은 그 이슈 안에서 먼저 한다. | 발견 즉시 나누지 않는다. 지연되거나 볼륨이 커졌고 따로 둘 가치가 있을 때만 나눈다. |
| 5 | 중단된 작업은 이슈 수를 줄인다. | 중단 중에는 막히는 것을 놓치지 않기보다 재개 때 한 번에 읽히는 응집도가 우선이다. |
| 6 | 사람은 설계를 리뷰하고, 가치는 TDD 로 지킨다. | 리뷰는 what · why · 설계 · 결정이 중심이다. AI 가 만든 값은 테스트 케이스로 설계대로인지 검사한다. 도메인 딥다이브는 생략하지 않는다. 배포 뒤 시나리오를 구체적으로 잡아 모호함 없는 예외를 다 찾고, 기술은 그 과정에서 들어간다(예: QoS 확인). 프레임워크 코드 수준은 기준이 아니다. |
| 7 | 빠르게 배포하고, 실패하면 이슈 단위로 되돌린다. | 빠른 반영으로 고객 반응을 확인한다. 이슈 하나가 머지 하나로 들어가 그 단위로 롤백할 수 있게 관리한다. 이슈 단위 롤백은 코드 머지 기준이고, 배포 롤백은 릴리스 단위라 이슈 하나만 되돌리려면 그 머지를 revert 해 다시 배포한다. 되돌릴 수 없는 변경(스키마 · 데이터)은 expand-contract 로 넣어 코드 revert 와 따로 움직이게 한다. 지나친 장애는 크리티컬하므로 테스트는 검출력 확인까지 확실하게 한다. |

## 기록과 판단

규칙 1 의 하루 기준은 가설이다. 적용하며 사례를 쌓고, 쌓인 사례로 판단해 고친다.

- **기록**: 하루 넘게 진행된 이슈는 전부 기록 대상이다. 기록 단계에서 거르지 않는다. 원천은 일일 기록이다. 완료되지 않은 이슈는 다음 날 일일 계획으로 이월되므로, 이슈마다 처음 들어온 날부터 완료로 빠진 날까지가 그대로 남는다.
- **판단**: 시점은 사용자가 정한다. 그 기간에 하루 넘게 진행된 이슈를 전부 뽑고, 사용자가 걸러 판정한다. 사유와 판정은 사용자 답만 적는다. 판단 결과로 규칙을 고치면 아래 이력에 날짜와 근거를 남긴다.

## 이력

| 날짜 | 변경 | 근거 |
|------|------|------|
| 2026-10-06 | 최초 수립. 이슈 하나는 하루 안에 끝내고, 넘기면 사유를 묻는다. 하루 안에 끝났어도 볼륨이 크면 같은 확인 대상이다. | 이슈를 끌고 가는 일이 반복되면 이슈 사이클이 너무 길다는 신호다. |
| 2026-10-15 | 루틴 · 비루틴을 나눈다. 비루틴은 이슈 하나를 며칠 끌고 Todo 체크리스트로 진행한다. 파생 건은 안에서 먼저, 중단 중에는 응집도를 우선한다. | 비루틴 작업에 하루 규칙을 그대로 적용하자 미정을 기다리며 나눈 이슈가 같은 결정 하나를 따로 기다렸다. 작은 크기를 지키는 관리 비용이 작업 시간을 잠식했다. |
| 2026-10-26 | 시범: 비루틴도 PR 은 이슈 하나에 하나. Todo 는 PR 안의 진행 단위. | Todo 마다 PR 로 나누면 같은 포트의 생산과 소비가 PR 사이에서 끊긴다. |
| 2026-10-29 | 시범을 확정한다. 코드 분량과 무관하게 이슈 하나를 피처 전체로 PR 하나에 담는다. 리뷰는 설계 중심, 가치는 TDD, 도메인 딥다이브로 모호함 제거, 실패는 이슈 단위 롤백. 과도기라 하이브리드다. | 생산 속도가 빨라져 PR 리뷰가 병목이 됐다 ([ADR-0032](adr/0032-one-issue-one-pr-review-design-not-code.md)). |
