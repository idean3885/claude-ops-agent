# ADR-0017: PR 플로우는 네 단계이고 머지 전에 원천을 다시 연다

- 상태: accepted
- 일시: 2026-09-30
- 관련: 이슈 #560, #520, `skills/flow/guides/pr.md` 「머지 전 최종 점검」

## 배경

PR 절차에 초안 생성(1)과 제출 전 자체 검증 · 스쿼시(2)는 있었다. 팀 리뷰를 받아 고치는 구간(3)은 「본문은 최종 내용과 같아야 한다」 한 문단이었고, 머지 직전에 전체를 다시 보는 단계(4)는 없었다. GATE 6 은 버전 파일만 대조한다.

실측에서 리뷰 반영 뒤 세 가지 어긋남이 머지 직전까지 갔다.

| 어긋남 | 사례 |
|--------|------|
| 설계 원천과 코드 | 상위 이슈의 설계 문서가 바뀌었는데 하위 PR 의 DDL 이 옛 설계(테이블 하나 · 자료형 · 컬럼 여러 개)를 담고 있었다 |
| 이슈와 코드 | 이슈 본문의 할 일 하나(문서 정리)가 PR 에 없었다 |
| PR 본문과 변경분 | 리뷰 반영마다 본문이 이력처럼 늘어 최종 변경분과 달라졌다 (다른 세션) |

세 어긋남의 공통 원인은 「앞 단계의 결과를 믿는다」이다. 자체 검증(2)을 통과한 뒤 리뷰 반영(3)으로 변경분이 바뀌면 설계 · 이슈 · 본문과의 대응은 모두 다시 어긋날 수 있는데, 그것을 다시 보는 자리가 없었다.

이 판단은 사람의 기억과 대화에만 있어 세션이 바뀌면 같은 누락이 반복됐다.

## 결정

### 1. PR 플로우를 네 단계로 적는다

초안 생성 → 자체 리뷰 · 수정 · 스쿼시 → 팀 리뷰 · 수정 → 최종 확정본 기준 전체 점검. 단계 표는 `pr.md` 가 갖는다.

### 2. 4단계는 이전 단계 결과를 믿지 않고 원천을 다시 연다

머지 요청 뒤 머지 명령 전에 네 쌍을 대조한다. 설계 원천 ↔ 코드 · 이슈 ↔ 코드 · PR 본문 ↔ 변경분 · 검증 자산(수동으로만 확인한 것이 남아 있는가). 토큰을 쓰더라도 생략하지 않는다.

### 3. 무엇을 열지는 절차가 정하지 않는다

「설계 원천」 · 「이슈 본문」 · 「PR 템플릿」이 무엇인지는 레포 · org 계층이 값으로 준다. 절차는 대조 방법만 갖는다.

### 4. PR 본문의 구조는 레포 · 팀 템플릿이 정한다

ops-agent 의 What · Why · How 템플릿은 레포에 템플릿이 없을 때의 기본값으로 내린다. ops-agent 가 갖는 것은 문장 규칙(What 추상화 · 금지 패턴)과 「본문 ↔ 변경분 일치」다. 결정자가 둘이면 언젠가 다르게 결정한다 (#520).

## 기각한 대안

| 대안 | 기각 이유 |
|------|-----------|
| 4단계를 별도 스킬로 둔다 | 실행 단위가 「머지 요청 → 머지 명령」 한 구간이고 GATE 6 이 이미 거기 있다. 같은 구간에 스킬 둘이면 순서가 대화에 의존한다 |
| 검증 자산 쌍을 빼고 셋만 둔다 | 사례에서 실제로 잡힌 결함이 「수동으로만 확인하고 레포에 남기지 않은 검사」였다. 나머지 세 쌍은 그것을 잡지 못한다 |
| 4단계가 여는 것을 매니페스트 키로 선언한다 | 이슈 템플릿 · 설계 링크 · PR 템플릿은 기존 요소(이슈 본문 규칙 · 이슈 본문의 링크 · 레포 템플릿)가 이미 갖는다. 키를 더하면 같은 값이 두 곳이다 |

## 대가

머지마다 원천을 다시 여는 비용이 든다. 사례 1에서 그 비용으로 결함 셋과 검증 자산 하나를 잡았다. 이 결정의 검증은 전문가가 아니라 사례가 한다. 이후 머지에서 4단계가 무엇을 잡았는지, 또는 아무것도 잡지 않았는지를 사례 2, 3으로 남긴다.
