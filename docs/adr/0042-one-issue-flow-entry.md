# ADR-0042: 이슈 플로우의 진입점은 flow 하나다

- 상태: accepted
- 일시: 2026-11-17
- 관련: #701, [ADR-0003](0003-declined-scope-router-and-wizard.md)(결정 1 의 「이슈」 겹침 행을 해소), [ADR-0028](0028-merge-owner-follows-impact-scope.md), [ADR-0040](0040-human-designs-and-decides-ai-ships-fast.md)

## 배경

여러 레포에 걸친 작업을 위해 org-flow 를 flow 와 별도 스킬로 두었다. 두 스킬이 이슈 시작 · 커밋 · PR 단계를 각자 적었다.

| 사실 | 출처 |
|------|------|
| 같은 단계를 두 스킬이 적어, 단계 이름 하나를 바꿀 때도 두 스킬을 함께 고쳤다. | #1069 |
| 트리거가 겹쳐 「이슈」 · 「PR」 요청이 어느 스킬로 갈지 갈렸다. 겹침을 막으려고 서브커맨드 이름을 트리거에 실었다. | ADR-0003 결정 1, org-flow 「트리거」 |
| 두 조직에서 org-flow 로 시작한 작업 22건 가운데 레포가 둘인 작업은 4건, 셋 이상은 0건이다. 상위 이슈가 있는 작업은 13건이고, 그 가운데 통합 브랜치(상위 이슈의 하위 작업을 모으는 브랜치)에서 분기한 작업은 1건이다. (#1078 정정: 처음에는 상위 이슈가 있는 13건을 통합 브랜치 사용으로 적었다) | 작업 상태 파일 실측 (2026-11-17) |
| 여러 레포에 걸쳐도 한 세션이 관련 레포를 모두 고친다. 사람은 설계를 보고, 구현은 봇 리뷰와 머지 준비 때의 검수가 맡는다. | 개발자 확정 |
| 조직 매니페스트의 이슈 트래커 지정(`providers.issue`)을 읽는 곳은 org-flow 하나다. flow 는 같은 매니페스트에서 커밋 표기 규칙만 읽는다. | 레포 전수 검색 |

## 결정

1. **이슈 플로우의 진입점은 flow 하나다.** 레포가 하나인지 여럿인지는 flow 가 작업 범위를 정할 때 갈리는 분기이고, 별도 스킬이 아니다.
2. **org-flow 의 고유 기능은 flow 의 여러 레포 가이드로 옮긴다.** 옮기는 것은 조직 매니페스트(셋업 · 이슈 트래커 지정 · 위치 해석), 작업 범위 산정, 메인 클론 갱신, 통합 브랜치, 레포별 워크트리 생성과 정리다. 조직 매니페스트가 이슈 트래커를 지정하면 flow 는 그 어댑터를 쓴다.
3. **사용 근거가 없는 기능은 옮기지 않는다.** 상태 조회 서브커맨드, 파이프라인 단계 추적, 프로젝트 로컬의 org-flow 확장 경로, 제출 때의 레포 간 계약 대조가 그것이다. 조직 매니페스트의 스크립트 대체는 워크트리 생성 · 정리 둘을 남긴다(#1078 정정: 처음에는 정리 하나만 남겼으나 외부 확장 조직이 생성 대체를 쓴다). 계약 대조는 한 세션이 관련 레포를 모두 고치므로 어긋날 자리가 없다.
4. **org-flow 는 안내만 남기고 비운다.** 외부 확장이 org-flow 를 진입 계약으로 읽고 있어, 그 확장이 flow 로 옮길 때까지 org-flow 는 flow 와 여러 레포 가이드를 가리키는 안내만 둔다. 트리거는 flow 로 옮긴다.
5. **상태 파일 이름은 그대로 둔다.** 이름의 `org-flow-` 접두는 정리 스크립트와 외부 확장이 읽는 형식이다. 이름을 바꾸면 진행 중인 작업의 상태 파일을 정리하지 못한다.

## ADR-0003 의 다시 열 조건

ADR-0003 에는 「다시 열 조건」 절이 없다(ADR-0040 결정 6 이전 기록). 바꾸는 이유를 적는다. ADR-0003 은 겹침을 남기고 사용자가 고르게 했다. 그 근거는 라우터의 유지 비용이 겹침의 비용보다 크다는 것이었다. 이 결정은 라우터를 들이지 않고 겹침 자체를 없앤다. ADR-0003 결정 1(라우터를 만들지 않는다)은 그대로다.

## 기각한 대안

| 대안 | 포기하는 것 | 얻는 것 | 기각 이유 |
|------|------------|---------|-----------|
| 지금 그대로 (스킬 둘) | 단계 문서 두 벌의 유지 · 트리거 경합 | 추가 작업 없음 | 단계 이름 하나를 바꿀 때도 두 스킬을 고쳤다(#1069). 레포 셋 이상 작업이 0건이라 따로 둘 근거가 약하다. |
| org-flow 를 지우기만 한다. | 통합 브랜치 · 조직별 이슈 트래커 지정 | 가장 작은 변경 | 통합 브랜치에서 분기한 작업이 있다(22건 중 1건). 이슈 트래커 지정을 잃으면 조직 트래커를 쓰는 작업이 기본 트래커로 간다. |
| org-flow 를 바로 지운다 (안내 없이). | 외부 확장의 동작 | 스킬 하나가 즉시 사라짐 | 외부 확장이 org-flow 를 먼저 읽는다. 확장이 옮기기 전에 지우면 그 흐름이 깨진다. |

## 결과

- flow 에 여러 레포 가이드를 두고, 이슈 시작 단계에서 조직 · 프로젝트 매니페스트가 있으면, 완료 단계에서 상태 파일이 있으면 그 가이드로 간다. 완료의 머지 확인은 이슈를 닫기 전에 한다.
- 세션 시작 트리거 표에서 org-flow 행을 뺀다. 「멀티레포」 · 「multi-repo」 · 「여러 레포」 · 「org 셋업」 · 「org 시작」 · 「org 완료」는 flow 트리거로 옮긴다. 「submit」 · 「서브밋」 · 「리뷰 요청」 · 「review request」는 옮기지 않는다. 제출은 flow 의 커밋 · PR 트리거가 받는다. 「org-flow」는 안내만 남은 스킬 이름으로 남는다.
- 포기하는 것: 상태 조회 서브커맨드, 파이프라인 단계 추적, 프로젝트 로컬 확장 경로, 레포 간 계약 대조, 워크트리 생성 · 정리 밖의 스크립트 대체.
- 안내만 남은 org-flow 는 외부 확장이 flow 로 옮긴 뒤 지운다.
