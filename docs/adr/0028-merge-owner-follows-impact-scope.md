# ADR-0028: 병합 주체는 반영 결과의 영향 범위로 정한다

- 상태: proposed
- 일시: 2026-10-14
- 관련: ADR-0018(승인 채널), ADR-0019(역할), ADR-0023(관찰된 효과), ADR-0029(최종 점검 기록의 자리 · 결과 표의 강제 수단 숙제를 정했다), #612 · #655(최종 점검 통과 기록)

## 배경

| 외부 근거 | 요지 |
|-----------|------|
| METR, 2025 | 한 벤치마크에서 보상 해킹 비율이 30.4% 였다. 「속이지 마라」 지시로 비율이 거의 줄지 않았다. |
| Huang et al., ICLR 2024 (초록 기준) | 외부 피드백 없는 자기 교정은 정확도를 올리지 못했다. |
| UTBoost, 2025 (초록 기준) | 테스트를 보강하자 통과 패치 일부가 오답으로 판정됐다. |
| Claude Code 모범 사례 | 지시문과 달리 훅은 결정적이다. |

이 레포도 같은 방향이다. ADR-0019 는 역할을 나눠 산출물을 자기 기준으로 승인하는 고리를 막았다. ADR-0023 은 효과를 관찰한 기록을 통과 조건으로 둔다. 병합 단계에는 이 원칙이 적용되지 않았다.

현행 flow 는 웹 병합을 기본으로 둔다. 다만 사용자가 머지를 승인하면 AI 가 `repo-merge` 갈래의 개방 명령을 제시한다. 사용자가 권한을 열면 AI 가 `gh pr merge` 를 실행한다. 이 경로의 통과 기록 요구는 #612 로 도입되어 2026-10-13 정식 규칙이 됐다 (#655).

남은 문제는 셋이다. 최종 점검을 실행한 AI 가 같은 통과 기록으로 머지를 실행한다. 추가 리뷰와 정리 중 하나를 고르는 사람의 자리가 정해져 있지 않다. 본인만 쓰는 저장소에도 같은 무게의 절차가 적용된다.

## 결정

### 1. 반영된 결과의 영향을 누가 받는가로 레포의 유형을 나눈다

| 유형 | 영향을 받는 쪽 | 반영 |
|------|----------------|------|
| 업무 | 동료 · 서비스 · 고객 | 사람이 병합한다. |
| 사상 | 이 플러그인을 쓰는 사용자 | 사람이 병합한다. |
| 저장소 | 본인 | AI 가 자율로 반영한다. |

유형은 사람이 레포의 성질을 보고 선언한다. AI 가 선언하면 자기 자율의 범위를 스스로 정하게 된다. 선언이 없는 레포는 유형이 틀려도 피해가 작은 업무 유형으로 본다. 성격이 섞인 레포는 더 엄격한 유형으로 선언한다.

### 2. 업무 · 사상 유형 레포에서 판단과 병합은 사람이 한다

마지막 병합을 사람이 해야 책임이 선다. AI 는 자체 검사 · 증거 수집 · 보고를 맡고 통과를 선언하지 않는다. ADR-0019 의 역할 분리를 병합 단계까지 넓힌 것이다. 사용자 승인 뒤 AI 가 병합하던 경로를 닫는다.

병합 자리의 기본값은 웹 UI 다. 형상 관리 도구에는 대개 웹 UI 가 있다 (GitHub · GitLab · Bitbucket 등). 사람은 웹에서 전체 변경을 마지막으로 보고 병합한다.

### 3. 업무 · 사상 유형 레포의 절차

| 단계 | AI | 사람 |
|------|----|------|
| 드래프트 | 자체 검사(테스트 · 불변식 · 자체 리뷰)를 실행한다. | 해당 없음 |
| 리뷰 | 리뷰 요청을 보내고 맥락 없는 AI 검토로 반례를 모은다. | 동료가 리뷰한다. |
| 머지 전 최종 점검 | 점검을 실행하고 증거를 모은다. | 해당 없음 |
| 상황 보고 | 결정 4 의 형식으로 보고한다. | 보고를 읽는다. |
| 판단 | 해당 없음 | 추가 리뷰를 받을지, 정리하고 병합할지 정한다. |

사상 유형 레포의 리뷰는 판단 단계에서 사람이 필요하다고 볼 때만 요청한다. 이 레포의 최근 병합 PR 10건은 리뷰가 0건이었다. 10건 중 10건을 본인이 병합했다.

### 4. 상황 보고는 주장마다 증거의 단계를 표시한다

| 단계 | 근거 | 증거로서의 무게 |
|------|------|-----------------|
| 0 | 자기 보고 | 증거로 쓰지 않는다. |
| 1 | 도구 반환값 (`ok` · 동기화 완료 표시) | 종료만 알린다. |
| 2 | 산출물 내부 일관성 | 산출물 안에서만 맞는다. |
| 3 | 결정적 검사 (테스트 · 불변식 · 가드) | 검출력이 확인된 경우에만 증거다. |
| 4 | 대상 시스템 독립 조회 | 효과를 관찰한 기록이다 (ADR-0023). |
| 5 | 출발점이 다른 검토 (외부 리뷰어 · 사람) | 독립 검증이다. |

맥락 없는 AI 검토는 반례 수집으로 보고한다. 원천을 열어 확인된 지적은 결함의 증거다. 통과의 증거로는 쓰지 않는다.

업무 · 사상 유형 레포의 보고는 사람의 결정 칸(「추가 리뷰」 · 「정리하고 병합」)으로 끝낸다. 저장소 유형 레포의 보고는 결정 칸 대신 반영 결과로 끝낸다.

### 5. 저장소 유형 레포의 변경은 AI 가 자율로 반영한다

반영 수단은 레포가 정한다. 반영 전에 결정적 검사를 실행해 알려진 결함을 거른다. AI 는 반영 결과를 보고에 남긴다. `gh pr merge` 로 반영하면 한시 권한과 통과 기록 요구를 그대로 따른다.

## 결과

| 대상 | 바뀌는 것 |
|------|-----------|
| 이슈 플로우(flow · org-flow)로 반영하는 레포 | 병합 주체, 상황 보고 형식, 사람의 판단 자리가 바뀐다. 유형 선언은 레포 성질을 두는 기존 자리(`.ops-agent/`)에 두고 AI 편집을 막는다. 업무는 기본값이라 공유 레포에는 선언 파일이 생기지 않는다. |
| 한시 권한 (ADR-0018) | 업무 · 사상 유형 레포에서는 훅이 `repo-merge` 갈래 개방을 거부한다. 승인 채널은 그대로다. |
| 최종 점검 통과 기록 (#612 · #655) | 업무 · 사상 유형 레포에서는 상황 보고의 첨부로 쓴다. 웹 병합 경로에서 점검을 강제할 수단을 정한다. |

각 항목은 후속 이슈로 구현한다. 레포 병합이 아닌 쓰기(이슈 트래커 · 위키)와 플러그인 플로우 밖의 작업은 이 ADR 밖이다.

대가는 둘이다. 업무 · 사상 유형 레포는 병합마다 사람이 웹을 한 번 연다. 강제 수단이 정해지기 전까지는 점검 실행 여부를 보고의 통과 기록 첨부로 사람이 확인한다. 저장소 유형 레포는 결정적 검사가 못 잡는 결함을 반영 뒤에 본인이 발견한다.

## 다시 열어야 하는 조건

| 조건 | 다시 볼 것 |
|------|------------|
| 저장소 유형 레포에서 결정적 검사가 못 잡은 결함이 반영된 사례가 반복된다. | 결정 5 의 자율 범위 |
| 웹 UI 가 없는 형상 관리 환경이 생긴다. | 결정 2 의 기본값 |

## 기각한 대안

| 대안 | 기각 이유 |
|------|-----------|
| 레포마다 같은 절차 | 결과를 본인만 받는 저장소에도 반영마다 웹 병합이 필요해진다. 1인 관리 환경에서 이 불편이 얻는 것보다 크다고 결정자가 판단했다. |
| 레포별 예외 나열 | 레포가 늘면 예외도 늘어난다. 왜 다른지가 문서에 남지 않는다. |
| 사용자 승인 뒤 AI 가 병합 | 병합의 책임이 사람에게 있다. 웹 병합이 대개 가능해서 이 경로가 주는 이득도 없다. |
