# ADR-0032: 이슈 하나를 피처 전체로 PR 하나에 담고, 사람은 설계를 리뷰한다

- 상태: accepted
- 일시: 2026-10-29
- 관련: #831

## 배경

이슈 가이드는 루틴하지 않은 작업을 Todo 마다 PR 하나로 닫게 했고, 한 이슈를 PR 여럿으로 닫는 절차를 두었다. 근거는 「한 이슈에 코드가 몰리면 리뷰 대상이 커져 전부 리뷰받는 것이 성립하지 않는다」였다. 사람이 코드를 줄 단위로 읽는다는 전제다.

그 전제가 바뀌었다.

- AI 가 코드를 쓰면서 생산 속도가 빨라졌다. 코드를 잘게 나눈 PR 을 사람이 하나씩 읽는 리뷰가 병목이 됐다.
- 일하는 방식은 AI 를 이기는 것이 아니라 같이 하는 것이다. 사람은 what · why 를 제대로 보고 설계에 신경 쓴다. how(코드)는 AI 가 쓰고 사람이 줄 단위로 읽지 않는 흐름이 대세다.
- 지향은 빠른 반영과 고객 반응 확인이다. 실패하면 빠르게 되돌린다.
- 지금은 과도기라 스탠스는 하이브리드다. 가치(value)는 테스트로 지키되, 도메인 딥다이브는 생략하지 않는다. 경험상 딥다이브를 건너뛰면 「그럴 수 있지 않나?」 같은 모호함이 남은 채 배포된다.
- Todo 마다 PR 을 내면 이슈가 여러 번 열린 채 남고, 같은 결정이 PR 사이에서 끊긴다. 같은 포트의 생산(어댑터)과 소비(검증)가 다른 PR 로 갈라진 사례가 있었다.

## 결정

| # | 결정 | 뜻 |
|---|------|----|
| 1 | 이슈 하나는 PR 하나다. | 이슈는 피처 단위 전체를 한 PR 로 끝낸다. 코드 분량은 이슈 · PR 을 나누는 기준이 아니다. Todo 는 PR 안의 진행 단위다. |
| 2 | 사람의 리뷰는 what · why · 설계가 중심이다. | 설계 원본과 결정 기록이 주된 리뷰 대상이다. 코드를 줄 단위로 읽지 않는다. |
| 3 | 가치는 TDD 로 지킨다. | AI 가 만든 값이 설계대로인지 테스트 케이스로 검사한다. 확정한 설계는 결정적 테스트로 고정하고, 되돌린 사본에서 실패하는지로 검출력을 확인한다. |
| 4 | 도메인 딥다이브로 모호함을 걷어낸다. | 배포 뒤 시나리오를 아주 구체적으로 잡고 모호함 없는 예외를 다 찾는다. 「그럴 수 있지 않나?」를 남기지 않는 것이 목표다. 기술은 그 다이브 과정에서 들어간다(예: QoS 확인). 설계에 필요한 개발 지식은 들고 있되, 프레임워크 코드가 어떻게 생겼는지는 기준이 아니다. |
| 5 | 빠르게 배포하고, 실패하면 이슈 단위로 빠르게 되돌린다. | 빠른 반영으로 고객 반응을 확인한다. 코드가 얼마든 이슈 하나가 머지 하나로 들어가 그 단위로 롤백할 수 있게 관리한다. 이슈 단위 롤백은 코드 머지 기준이다. 배포 롤백은 릴리스 단위라, 이슈 하나만 되돌리려면 그 머지를 revert 해 다시 배포한다. 되돌릴 수 없는 변경(스키마 · 데이터)은 expand-contract 처럼 앞으로만 가는 형태로 넣어 코드 revert 와 따로 움직이게 한다. 지나친 장애는 크리티컬하므로 테스트는 결정 3 의 검출력 확인까지 확실하게 한다. |

## 결과

- 이슈 가이드: 「Todo 하나를 PR 하나로」를 「Todo 는 PR 안의 진행 단위, 이슈는 PR 하나로 닫는다」로 바꾼다. 「PR 이 여럿인 이슈」 절차와 provider · PR 가이드의 `Refs #` 앞 PR 규칙을 지운다.
- 이슈 크기 · 진행 방식의 정본은 [태스크 관리 전략](../task-management.md)이다.
- 이슈를 나누는 기준은 리뷰 질문(설계 질문)이 달라지는가, 막히는 조건이 다른가로 남는다. 코드 분량 · 수정 파일 수는 기준이 아니다.
- 주장 검증(ADR-0030)은 이 결정의 짝이다. 사람이 코드를 줄 단위로 읽지 않는 대신 설계 항목 → 구현 → 테스트 대조가 리뷰의 근거가 된다.

## 기각한 대안

| 대안 | 지불하는 것 | 얻는 것 | 기각 이유 |
|------|-------------|---------|-----------|
| 지금 상태 (Todo 마다 PR) | PR 마다 리뷰 대기, 이슈가 여러 번 열린 채 남음, 결정이 PR 사이에서 끊김 | 사람이 한 번에 읽을 수 있는 PR 크기 | 사람이 코드를 줄 단위로 읽지 않으면 작은 PR 의 이점이 없다. 리뷰 대기가 생산 속도를 깎는다. |
| PR 크기에 정량 상한을 둔다. | 상한에 맞추려고 피처를 자르는 비용 | 기계적으로 지킬 수 있는 기준 | 상한은 코드 리뷰를 전제로 한 기준이다. 잘린 피처는 이슈 단위 롤백을 어렵게 한다. |
| 테스트에 전부 맡기고 도메인 딥다이브도 하지 않는다. | 설계에 필요한 개발 지식 | 리뷰 · 분석 시간 0 | 모호한 예외가 남은 채 배포되고, 테스트가 놓친 결함 앞에서 원인을 짚지 못해 되돌릴지 고칠지 판단하지 못한다. |
| 코드 리뷰를 유지하고 AI 생산 속도를 늦춘다. | 생산 속도 | 사람이 모든 코드를 본다는 안심 | 병목을 그대로 둔다. 안심은 테스트로 얻는 쪽이 결정적이다. |

## 다시 열 조건

- 테스트가 잡지 못한 결함이 운영 장애로 이어진 사례가 쌓인다.
- 이슈 단위 롤백이 실제로 되지 않은 사례가 나온다 (한 머지가 여러 이슈에 걸쳐 되돌리기 어려웠다).
