# ADR-0035: 글쓰기 자산을 기술 커뮤니케이션 하나로 통일한다

- 상태: accepted
- 일시: 2026-11-10
- 관련: #921, ADR-0019(역할), ADR-0020(PoC 구조), ADR-0021(전문가 근거와 노하우), ADR-0026(글쓰기 규칙은 레포에), ADR-0033(전문가는 결론 먼저)

## 배경

외부 팀에 보내는 짧은 문의와 답변에서 같은 실패가 이어졌다.

| 사례 | 실패 |
|------|------|
| 없는 기능의 제공 일정 문의 | 통신 구간 디테일을 넣었고, 걷어 내면서 두 항목 중 하나를 빠뜨렸다. |
| 프로젝트 없는 호출자의 조회 방법 문의 | 묻지 않은 보완 문장이 세 번 연달아 들어갔다. 구조는 「인사 → 불릿 → 질문을 다시 글로」였다. |
| 「이 API 가 왜 필요한가」 답변 | 물은 이유에 첫 줄로 답하지 못했고, 받는 쪽이 모르는 도메인을 설명하지 않았다. 원천을 다 찾기 전에 「없다」고 말했다. 사용자 교정이 한 답변에 여덟 번 들어갔다. |

세 사례 모두 낱말이 아니라 받는 사람이 그 글로 이해하고 움직일 수 있는가에서 실패했다. 이것을 판정할 자리가 없었다. 글쓰기 전문가는 낱말만 보고 구조 · 목적을 범위 밖에 뒀다.

글쓰기 자산은 규칙이 생길 때마다 덧붙여졌다. 전수 조사에서 드러난 상태는 다음과 같다.

| 상태 | 예 |
|------|-----|
| 같은 규칙이 여러 자리에 있다(30여 건). | em dash 금지 6곳, 합쇼체 5곳, 구두 시험 6곳, TL;DR 8곳, 콘텐츠 유형 분류 3벌 |
| 순서 규칙이 서로 부딪힌다. | 결론 먼저(V3 · ISS7 · ADR-0033)와 결론 뒤(ISS6 · PC1 · PC7) |
| 원칙에 규칙이 없다. | 묻기 전 확인, 아는 정보 → 새 정보의 문장 흐름, 근거와 결론을 잇는 논거 |
| 부르는 곳이 없는 자산이 있다. | 글쓰기 실무자(ADR-0019)를 부르는 스킬이 없다. |

## 결정

1. **개념은 기술 커뮤니케이션 하나다.** 엔지니어가 동료와 다른 팀에 보내는 글과 말이 뜻을 정확히 전하고(Weaver 의미 수준), 받는 쪽이 의도한 판단이나 행동을 하게 하는지(효과 수준)를 받는 사람 · 목적 · 맥락으로 판정한다. 미적 효과를 목표로 하는 글은 범위 밖이다. 보고 · 듣고 · 쓰고 · 말하는 일을 하나로 본다.
2. **원칙은 여덟 개다(TC1~TC8).** 생각이 먼저 · 받는 사람이 할 일을 먼저 · 항목 간 연계 · 흐름 · 받는 사람의 기억 · 근거와 결론의 연결 · 묻기 전 확인 · 말로 리허설이다. 정의와 원천은 [`experts/tech-comm.md`](../../experts/tech-comm.md) 다.
3. **순서 충돌은 받는 사람이 하는 일로 푼다.** 판단 · 행동할 사람에게는 결론을 먼저 두고, 검증할 사람에게는 질문 · 가설을 먼저 둔다. ADR-0020 이 PoC 리뷰에 정한 기준을 원칙(TC2)으로 올린다. 측정 보고(ISS6)와 PoC 리뷰(PC1 · PC7)는 검증이라 그대로 맞다.
4. **역할을 나눈다.**

   | 자리 | 맡는 것 |
   |------|---------|
   | 기술 커뮤니케이션 전문가. | 판정. 원칙 → 형식 규칙 색인을 둔다. 글쓰기 전문가를 대체하고 낱말 기준은 TC4 · TC8 아래로 들어간다. |
   | `config/style-rules/` | 기계로 검사할 수 있는 형식 |
   | `write` | 절차(계획 게이트 → 초고 → 퇴고). 초고 · 퇴고는 글쓰기 실무자에게 위임한다. |
   | `lint` | 등록된 규칙과 대조하는 검사 |
   | 글쓰기 실무자 | 집필 |

   위임하면 실행 순서는 실무자의 초고 · 퇴고 · 교정 → write 의 비평가 검토다. 비평가 검토에서 고친 부분만 교정을 다시 실행한다.

5. **중복은 원천 한 곳만 남긴다.** 나머지 자리는 「→ {파일} {ID}」 포인터로 바꾼다.
6. **파일 위치와 규칙 ID 는 그대로 둔다.** 세션 시작 미러, 금지 표현 훅, 카운터 스크립트, 이슈 구조 검사, 사내 쪽 연결 스킬이 style-rules 경로 · 규칙 ID · 헤딩 앵커를 직접 읽는다.

## 기각한 대안

| 대안 | 기각 사유 |
|------|-----------|
| 커뮤니케이션 전문가를 글쓰기 전문가와 따로 둔다. | 짧은 글 하나를 볼 때마다 두 전문가를 불러야 한다. 같은 문서에 두 전문가를 붙이면 같은 지적이 두 번 나온다(expert 스킬 「누구를 부르나」). |
| style-rules 에 체크리스트만 더한다. | 규칙은 등록된 위반만 잡는다. 「받는 사람이 무엇을 모르는가」, 「누구의 자산인가」는 판정이 필요하다. |
| 파일을 원칙별로 재배치한다. | 경로를 읽는 훅 · 스크립트 · 사내 쪽 스킬이 조용히 깨진다. 같은 효과를 색인과 포인터로 얻는다. |
| 이름을 「실용 글쓰기」 · 「비즈니스 글쓰기」로 한다. | 말하기가 빠지고, 실용문은 자기소개서 · 광고문까지 들어갈 만큼 넓다. |

## 다시 열 조건

- 전문가 판정이 lint 와 같은 지적을 반복해 내면, 그 갈래를 형식 규칙으로 내리고 전문가 기준에서 덜어 낸다.
- 시범 적용(짧은 글 10건)에서 사용자 교정 횟수가 줄지 않으면 원칙의 집행 자리(write 게이트 · 보내기 전 확인)를 다시 정한다.

## 결과

- 글과 말을 판정하는 자리가 하나가 된다. 짧은 글도 같은 원칙으로 판정한다.
- 규칙을 고칠 때 원천 한 곳만 고치면 된다.
- 기본 문체는 합쇼체를 유지한다. 규칙 문서 · ADR · 전문가 · 에이전트 정의는 한다체이고 스킬 문서는 파일의 기존 문체를 따른다(readability CJ2). 사내 쪽 스킬 이름 `content-write` 는 ADR-0006 에 따라 그 레포가 개명할 때 따라간다.
- 전문가 파일 이름이 바뀐다(`experts/writer.md` → `experts/tech-comm.md`). 기존 ADR 의 옛 경로는 시점 기록이라 고치지 않는다.
