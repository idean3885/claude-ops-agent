# 학습 과정 (시범 적용)

이해가 필요한 이슈를 진행하는 순서다. 2026-10-16 에 시범 적용으로 시작했고, 기록이 쌓이면 README 의 사고 플로우로 올린다 (#715). 그때까지 이 문서가 정본이고 세션 시작 훅이 `trials.local.json` 의 `learning-flow` 항목으로 주입한다.

## 왜 순서가 필요한가

- 자료를 모은 뒤 한 번에 다 설명받으면 글이 길고 모르는 용어가 많아 노이즈로 읽힌다. what · why 를 먼저 고정하고 거기서 넓혀야 이해가 남는다.
- 조각(설명 수준 규칙 · 다시 설명 · 전문가 · C4 · W2HO · 레슨런)은 다 있는데 순서가 없어 어시스턴트가 매번 다른 조합으로 답했다.
- 판정 기준은 하나다. **정리된 이슈 하나로 데일리 스크럼에서 간단명확하게 보고할 수 있는가.**

## 단계

폴리아의 문제 해결 4단계(이해 → 계획 → 실행 → 회고)에 대응한다. 역량에 따라 단계를 건너뛸 수 있지만, 건너뛰어도 되는 조건은 파일럿 기록으로 정한다 (드레이퍼스 숙련 모델: 생략은 숙련의 결과이지 플로우의 결함이 아니다).

| 폴리아 | 단계 | 하는 일 | 멈춤 · 판정 |
|--------|------|---------|-------------|
| 이해 | 1. 자료 수집 | 자산(knowledge · 참조)부터 검색하고 외부 자료를 모은다. | 0건이면 시도한 필터를 열거한다. |
| 이해 | 2. what · why | 각각 줄당 80자 안에서 적는다. how 는 적지 않는다. | 80자를 넘으면 범위가 넓거나 아직 구체화되지 않은 것이다. 이슈를 나누거나 더 좁힌다. |
| 계획 | 3. 확장 | C4 순서로 그려서 본다: 시스템 컨텍스트 → 컨테이너 → [컴포넌트]. 그림을 보고 토론하며 정정한다. | 2 에서 정한 관통 주제를 벗어나면 멈춘다. [컴포넌트] 는 막히거나 영향도를 재야 할 때만 내려간다. 그 아래(코드)는 그리지 않는다 (architecture AR2). |
| 실행 | 4. 보완 | 표 · 정돈된 형태로 그림을 보완하고 「그래서?」 결론으로 잇는다. 개념을 익히는 이슈면 대조군 표를 함께 둔다(아래 「대조군」). | 결론이 한 문장으로 나오지 않으면 3 으로 돌아간다. |
| 회고 | 5. 산출물 판정 | 결론인지, 사이클 없이 보관하는 위키인지 정한다. 다이어그램 최종본은 지면 활용을 보고 전부 유지할지 정리할지 판정한다. | 이슈 생성 때 가정으로 적고 진행 중 바꾼다. 하루에 몇 번 바뀌어도 된다. |

`[ ]` 는 생략할 수 있는 단계다. POSIX 명령 문법(SYNOPSIS) · EBNF 의 선택 요소 표기를 따른다.

회고 단계는 폴리아의 되돌아보기(looking back)다. 과정만 보는 애자일 회고와 달리 답의 검산과 방법의 일반화(이 방법을 다음에 어디에 쓰는가)까지 포함한다. 산출물 이름은 레슨런이다.

## 이해 루프

단계 2~4 안에서 돈다. 체화할 표현은 「기초부터 설명해 주세요」 하나다.

| 단계 | 말 | 무엇이 달라지나 |
|------|-----|----------------|
| 1 | (그냥 묻는다) | ELI15 설명 |
| 2 | 다시 설명해 주세요 | 같은 수준, 빠진 맥락부터 재설명 |
| 3 | 기초부터 설명해 주세요 | ELI10 전환, 한 문장에 하나씩 적층 |
| 4 | (토론) | 그림 · 표로 맞춰 가는 이해도 상승 |
| 5 | 원래 수준으로 | ELI15 복귀 |

2 · 3 의 순서는 바꿔도 된다. 용어를 몰라 막히면 3 이 먼저, 용어는 아는데 연결이 안 되면 2 가 먼저다.

## 대조군

개념을 익힐 때 대상 하나만 보지 않는다. 같은 문제를 다르게 푸는 대안을 대조군으로 두고, 차이와 그 이유를 나란히 본다.

| 무엇을 | 어떻게 |
|--------|--------|
| 대조군 고르기 | 같은 문제를 푸는 다른 제품 · 엔진 · 표준 두셋. 널리 쓰이는 것과, 요구가 다른 곳에서 쓰이는 것을 함께 고른다. |
| 비교 | 표 하나에 지원 여부 · 방식 · 왜 다른가를 행으로 둔다. 설명이 「이 대상에서는 이렇다」 한 줄로 끝나지 않게 한다. |
| 빈칸 | 확인하지 못한 칸은 「미확인」으로 둔다. 추정으로 채우지 않는다. |

예: MySQL 의 generated column 을 익힐 때 PostgreSQL · Oracle 을 나란히 둔다. 지원 종류(VIRTUAL · STORED), 인덱스 가능 여부, 이름이 다르고, 그 차이가 각 제품이 먼저 갖춘 기능(Oracle 의 함수 기반 인덱스 등)에서 나온다.

왜: 목적은 시험이 아니라 이해다. 대상 하나만 보면 그것이 전부인 줄 안다. 결정을 낼 때 택하지 않은 안을 대조군으로 두는 것과 같은 원리를 학습에 쓴다. 잊더라도 비교를 반복해 보면 감이 남는다.

## how 의 자리

「how 는 크게 중요치 않다」는 개발자의 가설이었고 아키텍트 문의로 판정했다.

| 판정 | 근거 |
|------|------|
| 이해 단계에서 how 는 기본 생략이다. | C4 정지 조건(architecture AR2): 컴포넌트 아래는 그 컨테이너를 고칠 사람이 있을 때만 그린다. 이해를 위한 그림은 컨테이너에서 멈추고, how 는 그 아래다. |
| how 를 더 보는 때는 막히거나 영향도를 재야 할 때다. | C4 와 같은 방식이다. 추상화된 개념부터 점진적으로 내려가다 막히거나, 되돌리기 비용 · 영향 범위를 재야 하는 디테일(외부 규격 · 동기 · 비동기 경계)이 나오면 그 자리만 추가로 확인한다 (architect AR6). 미리 전부 보지 않는다. |
| 산출물이 구현이면 how 는 플랜이다. | 그때는 이해 단계가 아니라 구현 단계이고 implement 가이드가 맡는다. |

「할 수 있는가」는 how 를 생략해서 치르는 비용이 아니다. 그것은 PoC 가 맡는 확인이고, 늦게 알았다면 PoC 가 부족했던 것이다 (spec 가이드: 미확인 전제는 PoC 결과 없이 확정하지 않는다). 산출물이 결론 · 위키면 how 는 끝까지 생략이고, 구현이면 플랜으로 들어온다.

## 줄당 80자의 근거

개인 기준이다. 한 줄을 읽기 편하다고 느끼는 길이가 80자 정도라 정했다. 줄 폭이 아니라 범위 신호로 쓴다: 한 줄에 판단 하나, 넘으면 범위가 넓거나 덜 구체화된 것이다. 외부 가독성 기준(WCAG 1.4.8, 한중일 40자)과는 다르다. 파일럿에서 최장 줄 길이를 관찰해 보정한다.

## 관찰 (시범 적용)

판정은 이슈 5건이 쌓이면 한다. 이슈마다 아래를 `trials.local.json` 의 log 에 한 줄씩 남긴다.

| 관찰 | 무엇을 보나 |
|------|-------------|
| 루프 횟수 | 한 이슈에서 이해 루프가 돈 횟수 |
| 복귀 | 「기초부터」 뒤 「원래 수준으로」 복귀 여부 |
| 다이어그램 | 3 단계에서 C4 다이어그램이 그려지고 토론에 쓰였는지 |
| 생략 | 건너뛴 단계와 그래도 결과가 같았는지 |
| 보고 | 그 이슈 하나로 데일리 스크럼 보고가 됐는지 |
| 줄 길이 | what · why 최장 줄의 글자 수. 5건 뒤 80자를 확정하거나 바꾼다 |
