# 설계 배경과 의사결정 기록

claude-ops-agent 가 왜 이런 구조인지, 어떤 선택지 중 무엇을 왜 골랐는지에 대한 기록입니다. 기능 목록은 [README](../README.md) 에 있고, 이 문서는 그 뒤의 결정을 다룹니다.

## 출발점

AI 에게 코드를 맡기면서 제 역할이 "코드 작성"에서 "의사결정과 검증"으로 옮겨갔습니다.

문제는 AI 가 매번 같게 동작하지 않는다는 점입니다. 같은 요청에도 톤이 흔들리고, 어제 합의한 규칙을 오늘 잊고, 묻지 않은 수식어를 붙입니다. 매번 사람이 교정하면 그 교정 자체가 일이 됩니다. 이 반복을 어떻게 줄일지가 아래 결정들의 공통 배경입니다.

## 결정 1. 한 플러그인에 담는 범위

기능별로 플러그인을 나눠 두는 방식으로 시작했습니다. 이슈 플로우, 콘텐츠 검증, 교차 검증, 사용량 추적이 각자 별 플러그인이었습니다.

| 선택지 | 문제 |
|--------|------|
| 기능별 분리 유지 | 도구 하나는 가볍지만, 세션마다 여러 플러그인의 컨텍스트·설정을 따로 관리하고 규칙이 흩어진다 |
| **단일 통합** | 한 플러그인이 무거워진다. 대신 관리 지점이 하나로 줄고 규칙이 한 곳에 모인다 |

통합을 골랐습니다. 판단이 바뀐 계기는 제약 조건의 변화입니다. 컨텍스트 창이 1M 으로 늘고 모델·캐싱이 개선되면서, 무겁게 통합해도 인덱스만 상시 싣고 상세는 진입 시점에 읽는 방식으로 감당할 수 있게 됐습니다. 그래서 관리 지점 축소와 규칙 일원화를 경량성보다 앞에 뒀습니다.

레이지 로딩은 실제로 이렇게 적용했습니다. 스킬 단계 가이드는 `skills/flow/guides/` 에 두고 단계 진입 시에만 읽습니다. 문헌 근거(`config/style-rules/references/`)와 지표 정의(`config/style-rules/metrics/`)는 세션 시작 미러 대상에서 제외하고 추적이 필요할 때만 참조합니다. 무겁게 통합하면서 세션 예산을 지키는 방법이 곧 이 결정의 조건이었습니다.

### 그럼 갈라 두는 자리

전부 한 플러그인에 넣지는 않았습니다. 갈라 두는 기준은 **재사용 범위와 노출 경계**입니다.

| 계층 | 담는 것 | 갈라 둔 이유 |
|------|---------|--------------|
| 공통 (이 레포) | 워크플로우 골격, 트래커 추상화, 작성 규칙, 차단 규칙 | 조직과 무관하게 재사용된다. 공개해도 문제없다 |
| 조직·개인 | 조직 전용 시스템 어댑터, 개인 데이터 원천 | 공개 표면에 둘 수 없다 |
| 팀·프로젝트 | 언어 컨벤션, 브랜치 규칙, 태스크 템플릿 | 팀마다 다르고, 팀 단위로 배포·갱신된다 |

공통 계층이 트래커를 provider 로 추상화하고 작성 규칙을 세션 시작에 미러하기 때문에 이 분리가 성립합니다. 특화 계층은 공통 계층의 골격을 그대로 쓰고 자기 조직·팀에 맞는 정의만 채웁니다.

## 결정 2. 규칙을 두는 자리

| 선택지 | 문제 |
|--------|------|
| 사람이 기억한다 | 잊힌다 |
| 문서에 적어 둔다 | 안 읽힌다 |
| **하네스에 심는다** | 초기 구성 비용이 있으나 매번 자동 적용된다 |

세 번째를 골랐습니다. 규칙을 세 시점(세션 시작·파일 편집·응답 직전)에 자동으로 걸리게 두면, 작업 중에 "이 레포는 규칙이 뭐였지"를 다시 떠올릴 필요가 없습니다. 사람이 지키는 규칙은 안 지켜지는 순간을 막지 못하지만, 환경이 먼저 깔아 두면 저와 AI 가 매번 같은 출발선에 섭니다.

### 주입 지점 세 곳

**SessionStart**: `scripts/session-start.mjs` 가 세션이 열릴 때 한 번 실행됩니다.

| 동작 | 막는 실수 |
|------|-----------|
| provider 감지 (git remote host → 이슈 트래커 정의) | 트래커별 API 방식 추측 |
| git identity 자동 설정 (provider 기준) | 다른 계정으로 커밋 |
| 스타일 SSOT 미러 (`config/style-rules/` → `~/.claude/ops-agent/style-rules/`) | 작성 규칙이 레포마다 제각각 |
| 유저 스코프 자원 자리 만들기 (`~/.claude/advisor/profiles/` 등) | 스킬이 자기 계약의 전제를 못 갖춰 첫 사용이 매치 실패로 끝남 |
| 버전 동기화 + git 자동 복원 | 캐시 디렉토리 버전 불일치 |

**hook**: 매 편집·매 응답에 규칙을 겁니다.

| hook | 시점 | 동작 |
|------|------|------|
| `forbidden-words-prompt.sh` | UserPromptSubmit | 금지 표현 룰을 사전 주입 |
| `forbidden-words-stop.sh` | Stop | 직전 응답 위반을 다음 턴에 통지 |
| `lint-posttool.sh` | PostToolUse (Edit/Write) | 문서 편집 후 자가 점검 유도 (마커 opt-in, `_posts/` 는 무조건) |
| `pre-tool-use.mjs` | PreToolUse | 퍼블릭 표면으로 가는 대외비 키워드 하드 차단 |

**스킬**: 워크플로우 순서를 강제합니다. `flow`(이슈 → spec → 구현 → commit → PR), `write → lint → publish`, `cross-verify`(멈추고 네 관점 확인). 직접 호출하지 않고 자연어 트리거로 이어지므로, 순서를 사람이 기억하지 않아도 됩니다.

## 결정 3. 표현 가드: 차단 대신 자가 대조

처음엔 응답 출력 직전에 금지 표현을 막는 방식을 떠올렸습니다. 두 가지가 걸렸습니다. 정규식이 문맥을 못 읽어 정상 표현을 오탐하고, 막힌 자리를 자동으로 메우면 의미가 틀어집니다.

그래서 막지 않고 **사전 주입 + 사후 통지**로 바꿨습니다. hook 은 룰을 미리 깔고(prompt) 위반을 알려 줄 뿐(stop), 최종 판단은 어시스턴트가 출력 직전에 직접 대조해서 내립니다. 도구가 사람의 판단을 대체하는 게 아니라, 판단할 자리를 좁혀 줍니다.

## 결정 4. AI 티 분류: 자체 작성과 차용

AI 가 쓴 한국어는 특정 패턴을 반복합니다.

| AI 티 갈래 | 예 |
|------------|-----|
| 영어 번역투 | "~을 통해" |
| 근거 없는 단언 | "보장합니다" |
| 과시성 수식어 | "고수준의" |
| 의미 없는 형용사 | "원활하게" |

분류 골격은 [`epoko77-ai/im-not-ai`](https://github.com/epoko77-ai/im-not-ai)(MIT) 의 A~J 10대 카테고리를 차용하고, 한국어 기술 문서 맥락의 처방·예시는 자체 작성했습니다. 검증된 골격을 다시 짜는 대신 차용하고 한국어 특화 부분에만 힘을 쏟는 선택입니다.

분류만으로는 안 지켜집니다. 그래서 두 가지를 걸었습니다.

- 즉시 교정 가치가 있는 S1 패턴만 표현 가드 hook 의 정규식 룰로 등록
- 분류 체계와 hook 룰을 카테고리 ID 로 1:1 매핑해 룰이 왜 존재하는지 역추적되게 함

## 결정 5. 1인 개발의 이슈 플로우 강제

1인 개발이면 이슈·PR 을 생략하고 바로 커밋하고 싶어집니다. 그래도 강제하기로 했습니다. 변경 이력이 이슈 번호로 묶여야 나중에 추적되고, "변경 = 버전업" 원칙이 흐트러지지 않습니다. 자연어로 "이거 고쳐줘"라고 해도 `flow` 가 이슈 생성부터 PR·버전 범프까지 한 흐름으로 끌고 갑니다.

## 결정 6. 규칙 묶음이 커졌을 때의 구간별 처방

`config/style-rules/` 가 2,933줄(base 1,622 + extensions 1,311)까지 자랐습니다. AI 티 제거와 윤문에서 출발해 필요할 때마다 찾아 붙인 결과라, 전면 재작성을 검토했습니다.

실측해 보니 볼륨의 원인이 한 가지가 아니었습니다.

| 구간 | 원인 | 처방 |
|------|------|------|
| `extensions/` | 골격 부재. 9개 파일이 `적용 대상`·`필수 구조`·`base 대비 적용 강도`·`합격선` 네 절을 예외 없이 반복하고 그중 셋은 값을 채우는 자리 | 전면 개편. 세 절을 `profiles.md` 표로 흡수 |
| `base/` | 예시 누적. 예시 블록이 `tone` 35%, `punctuation` 33%, `readability` 24% | 증분. 규칙이 엉킨 게 아니라 각 규칙이 근거로 예시를 달고 있어 길어진 것이고, 걷어내면 규칙이 흐려짐 |

전체에 하나의 처방을 정하려던 것이 잘못 세운 질문이었습니다. 원인이 구간마다 다르면 처방도 구간마다 다릅니다.

`base/` 를 재작성하지 않은 결정적 이유는 따로 있습니다. 재작성 비용이 전부 이쪽에 몰려 있습니다. `forbidden-words.json` 14룰이 `ai-tells` 카테고리 ID 와 1:1 로 물려 있고(결정 4), im-not-ai 차용 추적도, 외부 소비자 참조도 `base` 쪽입니다. 80개 ID 를 다시 매기면 이 셋을 같은 시점에 고쳐야 합니다.

ID 충돌은 실제로 있었습니다. `readability` 의 `K1~K3`(CJK)가 `knowledge.md` 의 `K1~K3` 와, `B1`(blockquote)이 `blog.md` 의 `B1~B10` 과 같은 글자였습니다. 전체 재번호 대신 충돌하는 4개만 `CJ1~CJ3`·`BQ1` 로 바꿨습니다. 결함 하나 때문에 80개를 건드리지 않습니다.

## 결정 7. 에이전트가 읽는 문서의 규칙 자리

`style-rules` 는 사람이 읽는 한국어 산문만 다뤘습니다. `SKILL.md`·`CLAUDE.md`·단계 가이드처럼 에이전트가 읽는 문서에는 기준이 없어, 길이와 계층과 완료 조건이 작성자 재량이었습니다.

[`mattpocock/skills`](https://github.com/mattpocock/skills) 의 `writing-for-agents`(MIT) 를 대조해 보니, 여덟 항목 중 다섯이 이 레포에 없었습니다. 나머지 셋은 이미 있었습니다. 단일 출처는 레포 운영 원칙이고, "환경이 곧 출처"는 결정 2 의 다른 표현이며, 가지치기는 `length.md` 가 부분적으로 다룹니다.

새 디렉토리를 만들지 않고 `base/authoring.md` 파일 하나로 넣었습니다. 표면을 하나 더 만들면 "이 문서는 사람용인가 에이전트용인가"를 매번 먼저 판정해야 하는데, `SKILL.md` 는 둘 다입니다. 그리고 차용하려는 문서 자체가 침전(더하기는 안전해 보이고 빼기는 위험해 보여 낡은 층이 쌓이는 것)을 실패 모드로 지목합니다. 새 디렉토리로 어펜드하는 건 그 문서가 하지 말라는 동작입니다.

한 항목은 그대로 들이지 않았습니다. 부정 지시가 금지 대상을 컨텍스트로 끌어와 오히려 활성화한다는 지적은 `forbidden-words.json` 과 정면으로 걸립니다. 다만 이 레포의 가드는 출력을 막지 않고 룰마다 `대체` 필드로 긍정형 처방을 함께 싣는 구조라(결정 3) 성격이 다릅니다. 원칙만 `AU5` 로 등재하고 기존 가드는 유지했습니다.

## 이후 수정

첫 결정이 늘 옳지는 않았습니다. 실제로 되돌린 것들입니다.

- **릴리즈 자동화**: 초기 스크립트는 머지 후 main 에 직접 push 했습니다. 안전하지 않아, main 직접 push 를 제거하고 버전 범프를 PR 안에서 처리하는 방식(`post-merge-sync.sh`)으로 축소했습니다.
- **README**: 기능을 빠짐없이 나열하려다 장황해졌습니다. 가치 우선 구조로 두 번 재정돈(#109, #116)하고, hook·설정 상세는 `docs/` 로 분리했습니다. 세 번째 재정돈(#230)에서는 산문을 표로 바꾸고, 규칙 본문 대신 정본 링크만 남기고, 규칙의 문헌 근거를 표면으로 올렸습니다. 정체 한 줄도 "개인 작업 비서"에서 "규칙을 계층으로 나눠 배포하는 에이전트"로 바꿨습니다. 도구 설정을 가리키는 말로는 계층 구조를 담지 못했습니다.
- **톤 규칙**: 방어적·변명조 프레이밍과 과장을 막는 톤 규칙(T14)을 뒤늦게 추가했습니다.

규칙을 환경에 고정한다는 접근은 유지하되, 개별 규칙은 쓰면서 어긋난 지점을 찾아 고쳤습니다.

## 남는 것

도구는 바뀝니다. AI 모델이 더 좋아져도 "합의한 원칙을 환경에 고정한다"는 접근은 그대로 적용됩니다. 규칙이 사람 머릿속에 있으면 잊히고 문서에만 있으면 안 읽히지만, 하네스에 있으면 매번 자동으로 걸립니다. 그래서 규칙을 README 가 아니라 SessionStart·hook·스킬에 둡니다.
