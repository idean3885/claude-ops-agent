# 표준 용어

대화와 문서에서 한 개념을 한 말로 부르기 위한 목록이다. 용어 교정(전역 지침 「용어 교정」)으로 바로잡은 말이 세션 마무리 때 여기 올라온다. 이 목록이 원천이다. 같은 말이 로컬 메모리 · 프로젝트 문서에 따로 있으면 여기로 옮긴다.

## 등재 조건

- 항목마다 문장 시험(tone T5)의 글 예문과 말 예문을 하나씩 둔다. 제목의 표준 용어가 두 예문에 모두 들어간다.
- 말 예문이 필수인 이유: 글로 이해한 것을 남에게 설명할 때 사람은 말로 한다. 말로 해서 어색한 용어는 전달하는 자리에서 다른 말로 바뀌고, 다시 섞인다.
- 말로 했을 때 어색하면 등재하지 않고 다른 말을 고른다.
- 공개할 수 없는 사내 용어는 올리지 않는다.
- 겪은 사례나 딥다이브한 기록이 있는 말만 올린다. 정의만 알게 된 말은 언제 · 왜 쓰는지 설명하지 못해 아는 척으로 남고, 목록이 학습 목록이 아니라 용어집이 된다. 사례에는 비공개 맥락이 들어가므로 이 목록에는 규칙만 두고, 용어와 사례를 잇는 연결은 소비 프로젝트가 정한 비공개 자리에 둔다.
- 다른 세트: 같은 구조를 다른 분야 · 다른 제품이 다른 말로 부르는 세트를 「다른 세트」 칸에 적는다. 이 항목의 말과 같은 글자를 쓰거나, 그 세트의 말을 이 개념에 섞은 기록이 있을 때만 적는다. 다른 세트는 등재가 아니라 이 항목의 구분을 돕는 줄이라 사례 조건을 따로 받지 않고, 집계 · 제거 대상도 아니다. 그 세트를 그 세트의 자리에서 섞어 쓰면 그때 항목으로 등재한다.
- 같은 분야 안에서 한 글에 함께 놓이는 말(통합 테스트와 e2e 테스트처럼 범위가 다른 자리)은 다른 세트가 아니다.
- 다른 세트가 목록의 항목이면 두 항목이 서로를 적는다.
- 검출: 등재한 뒤에도 답에서 다시 섞이는 말은 「검출」 칸에 대상 낱말 · 정규식 · 표준 용어를 단다. 입력 훅이 대상 낱말과 표준 용어를 매 턴 짧게 실어 답을 쓰기 전에 막고, 응답 검사 훅은 직전 답에서 그 정규식을 찾아 재발을 센다. 정규식은 섞어 쓴 뜻으로 쓴 자리만 잡게 좁힌다. 같은 글자의 다른 뜻까지 잡으면 맞게 쓴 답에도 교정이 붙는다. 검출 · 비검출 예문은 `scripts/selftest-forbidden-words.py` 에 둔다.
- 형식 검사: `python3 scripts/terms.py check`. 등재 절차는 `skills/learn` 「용어 교정 등재」

## 제거 조건

- 다 익힌 항목은 「## 익힌 항목」 절로 옮기고 `- 익힘: YYYY-MM-DD` 를 붙인다. 지우지 않고 보관하며 세션 시작 때 주입하지 않는다. 다시 헷갈리면 「## 항목」으로 되돌린다. 되돌릴 때 `익힘` 줄을 지우고 `등재` 를 되돌린 날로 바꿔 집계를 새로 시작한다. 그러지 않으면 되돌린 원인이 된 교정이 오답으로 남아 다시는 제거 후보가 되지 못한다. 되돌아오는 과정도 학습이다.
- 제거 후보는 정답률 100% 이고 등재 다음 날부터 서로 다른 세션 3개 이상에서 다룬 항목이다. 정답률은 그 항목을 다룬 세션(용어가 모두 나왔거나 그 항목으로 교정받은 세션) 중 교정받지 않은 비율이다. 레슨런 지표의 정답률([lessons.md 「지표」](../../../docs/lessons.md#지표))과 같은 개념이고, 단위가 답이 아니라 세션이다. 한 세션의 교정은 여러 번이어도 하나다.
- 두 용어로 된 항목은 두 용어가 모두 나온 세션만 사용으로 집계한다. 한쪽이 일반어면 한쪽만 집계할 때 정답률이 부풀려진다.
- 항목 수에는 상한을 두지 않는다. 세션 시작 때 주입하는 것은 항목당 한 줄(표준 용어 · 섞어 쓴 말 · 다른 세트 이름)의 인덱스이고, 구분 · 예문은 교정할 때 원천에서 읽는다. 비용과 효과는 항목마다 생기므로 개수가 아니라 항목별 정답률로 판정한다.
- 집계: `python3 scripts/terms.py stats`. 「## 항목」 절만 집계한다. 옮기는 것은 사람 확인 뒤에 한다.

## 항목 형식

```markdown
### 표준 용어 (둘로 나눈 개념이면 「A · B」)
- 섞어 쓴 말: 사용자가 섞어 쓴 말과 그때 가리킨 개념
- 구분: 각 용어가 무엇을 가리키는지 한두 문장
- 글: 「문서에 쓰는 문장」
- 말: 「입으로 설명하는 문장」
- 다른 세트: 「세트 이름」(쓰는 곳) 이 항목과 갈리는 지점 한 문장. (선택. 같은 구조를 다른 분야가 다른 말로 부를 때만)
- 검출: 「섞어 쓴 말」 `정규식` → 「표준 용어」 (선택. 등재한 뒤에도 답에서 다시 섞일 때만)
- 등재: YYYY-MM-DD
- 익힘: YYYY-MM-DD (「## 익힌 항목」으로 옮길 때만)
```

## 항목

### 스키마 · 테이블 정의
- 섞어 쓴 말: 스키마(「테이블」 없이 단독으로 테이블 하나의 구조를 가리킬 때)
- 구분: 스키마는 테이블을 담는 그릇이다. MySQL 에서는 데이터베이스와 같은 말이고 Flyway 이력도 스키마마다 하나다. 테이블 정의는 컬럼 · 인덱스 · 콜레이션 같은 테이블 하나의 구조다. 개발자 간 의사소통에서는 「테이블 스키마」가 굳어진 컨벤션이라 그대로 쓴다. 한 글에서 스키마를 그릇의 뜻으로도 쓰면 테이블 정의로 바꾼다.
- 글: 「알파 · 베타 두 스키마에 같은 테이블 정의를 적용했다.」
- 말: 「알파랑 베타 스키마 둘 다 테이블 정의를 똑같이 맞춰 놨어요.」
- 등재: 2026-10-21

### envelope
- 섞어 쓴 말: `봉투`(직역) · 응답 바디(본문 전체를 가리키는 다른 개념) · 감싼 객체(번역 시도)
- 구분: 실제 내용(payload)을 감싸는 바깥 층이다. 응답 바디는 본문 전체라 다르다. 번역하지 않고 글로는 envelope, 말로는 「엔벨로프」라고 한다. 「그게 뭔가요?」 하면 이 정의로 설명한다.
- 글: 「오류 응답도 같은 envelope 의 error 필드에 담는다.」
- 말: 「에러도 같은 envelope 안 error 필드에 들어가요.」
- 등재: 2026-10-21

### 도메인 · 애그리거트 루트
- 섞어 쓴 말: 도메인(컨트롤러 URL 의 `resource-quotas` 를 가리킬 때) · 애그리거트 · 루트
- 구분: 도메인은 업무 영역 전체이고 모듈 하나에 대응한다. 애그리거트는 한 트랜잭션에서 함께 바뀌는 묶음이고, 애그리거트 루트는 그 묶음에 들어가는 유일한 입구 엔티티다. REST URL 의 컬렉션 리소스는 보통 애그리거트 루트에 대응하고, 그 아래 하위 경로는 루트를 좁히는 범위다.
- 글: 「상품 활성화 도메인에서 리소스 쿼터는 애그리거트 루트이고, `resource-quotas` 경로가 이 루트에 대응한다.」
- 말: 「상품 활성화가 도메인이고, URL 의 resource-quotas 는 그 안의 애그리거트 루트예요.」
- 등재: 2026-10-21

### 플러시 · 커밋
- 섞어 쓴 말: 「커밋하고 플러시」(순서를 바꿔 부름)
- 구분: 플러시는 JPA 영속성 컨텍스트에 쌓인 변경을 SQL 로 DB 에 보내는 것이고, 커밋은 트랜잭션을 확정하는 것으로 DB 트랜잭션 커밋과 같다. 트랜잭션이 끝날 때 플러시가 먼저, 커밋이 뒤다. DB 의 유니크 방어는 플러시 여부와 무관하게 일어나고, 플러시가 정하는 것은 위반이 어느 시점에 드러나느냐다.
- 글: 「트랜잭션이 끝날 때 플러시가 INSERT 를 먼저 보내고, 커밋이 그 결과를 확정한다.」
- 말: 「끝날 때 플러시로 쿼리를 먼저 보내고, 그다음에 커밋해요.」
- 등재: 2026-10-21

### 포트 계약 · HTTP 상태
- 섞어 쓴 말: 「포트 계약에서 409 를 주기로 약속했다」
- 구분: 포트 계약은 도메인 예외(예: 중복 예외)까지만 약속하고 HTTP 를 모른다. HTTP 상태는 웹 경계가 그 예외에 매핑한 표현이다. 같은 포트를 배치가 부르면 상태 코드 없이 예외만 받는다.
- 글: 「포트 계약은 중복 예외를 약속하고, 409 같은 HTTP 상태는 웹 경계가 그 예외에 매핑한다.」
- 말: 「포트 계약은 예외까지만 약속해요. HTTP 상태 409 는 웹 쪽에서 정해요.」
- 등재: 2026-10-21

### expand-contract
- 섞어 쓴 말: 확장 · 수축(번역), 「v2 로 올리기」(운영 중 형식 전환을 가리킬 때)
- 구분: 스키마를 바꿀 때 새 구조를 먼저 더하고(expand) 애플리케이션이 옮겨 간 뒤 옛 구조를 지우는(contract) 패턴이다. Martin Fowler 는 Parallel Change 로 정리했다. 번역하지 않고 글로는 expand-contract, 말로는 「익스팬드 컨트랙트」라고 한다.
- 글: 「컬럼 변경은 expand-contract 로 나누고, expand 단계에서는 옛 컬럼을 지우지 않는다.」
- 말: 「이건 expand-contract 로 가서 expand 까지만 먼저 배포해요.」
- 등재: 2026-10-21

### 직렬화 · 역직렬화
- 섞어 쓴 말: 직렬화 실패(읽는 쪽이 값을 복원하지 못한 상황을 가리킬 때)
- 구분: 직렬화는 객체를 저장 · 전송할 바이트로 바꾸는 쓰는 쪽의 일이고, 역직렬화는 그 바이트를 다시 객체로 되살리는 읽는 쪽의 일이다. 클래스 이름 변경이나 모르는 필드 때문에 깨지는 것은 대부분 읽는 쪽이라 역직렬화 실패다. 실패 쪽을 바꿔 부르면 원인을 쓰는 쪽에서 찾게 된다.
- 글: 「클래스 패키지를 옮긴 새 버전이 옛 캐시 값을 읽다가 역직렬화에 실패했다.」
- 말: 「쓸 때는 멀쩡했는데 새 버전이 읽을 때 역직렬화가 깨졌어요.」
- 등재: 2026-11-26

### 복구 비용 · 롤백 가능
- 섞어 쓴 말: 되돌리는 비용(구어. 「되돌리기 비싼」 같은 변형 포함), 가역성(용어 후보로 제안된 말), 되돌리기(롤백을 가리킬 때), 롤백 가능(정의 없이 「복구 비용이 낮다」 · 「피해가 작다」를 가리킬 때)
- 구분: 복구 비용은 행위가 잘못됐을 때 원래 상태로 돌려놓는 데 드는 비용이다. AI 에게 줄 호출 권한을 이 비용으로 나눈다. 복구 비용이 낮은 조회는 열고, 높은 변경(생성 · 수정 · 삭제)은 계획을 보여 주고 허락을 받는다. 롤백 가능은 롤백하면 실행 전 상태로 돌아오고 지울 수 없는 사이드 이펙트가 남지 않는다는 뜻이다. 판정 질문은 「롤백한 뒤에도 지울 수 없는 사이드 이펙트가 남는가」 하나이고, 그런 사이드 이펙트는 남이 이미 본 것(알림 · 공개 · 유출), 남이 이미 받은 것(배포 · 릴리즈), 원본이 사라진 것(삭제 · force push · 덮어쓰기) 셋이다. 둘은 다른 축이다. 잘못 보낸 메일은 복구 비용이 낮아도 롤백 불가이고, 아무도 쓰지 않은 DB 를 백업에서 복원하는 일은 복구 비용이 높아도 롤백 가능이다. 피해의 크기(영향도 · 장애 규모)는 둘 다 아니다. 판정은 레포가 아니라 행위 단위로 한다. 같은 push 도 개인정보가 담기면 이력에 남아 롤백 불가다. 롤백 가능한 행위도 롤백 전까지 사이드 이펙트가 쌓이고(이미 겪은 장애 시간), 남이 그 결과 위에서 다음 행동을 하면 롤백 불가로 바뀐다.
- 글: 「호출 권한은 복구 비용으로 나누고, 사람이 판단할 결정은 롤백 가능한지로 나눈다. 롤백 가능은 롤백한 뒤 지울 수 없는 사이드 이펙트가 남지 않는다는 뜻이다.」
- 말: 「복구 비용이 싸도 메일은 롤백 가능이 아니에요. 이미 읽었으니까요.」
- 다른 세트: 「Type 1 · Type 2 결정」(Amazon. 「단방향 문 · 양방향 문」이라고도 부름) 결정 단위로 부르는 말이다. 롤백 가능은 그 결정이 실행하는 행위 하나를 판정한다.
- 검출: 「되돌리는 비용」 `되돌리(?:는|기)\s?(?:비용|값)|되돌리기\s?(?:비싼|싼|어려운|쉬운)` → 「복구 비용」
- 등재: 2026-11-26

### 사이드 이펙트

- 글: 「리뷰어 지정은 알림이라는 사이드 이펙트를 남겨 롤백 가능이 아니다.」
- 말: 「이거 머지하면 사이드 이펙트 없나요?」
