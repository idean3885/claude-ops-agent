# 마크다운 가독성 규칙 (base)

기술 블로그·위키·이슈·PoC 등 모든 한국어 마크다운 문서의 구조 가독성 SSOT.

> **출처**: Google Developer Documentation Style Guide, Microsoft Writing Style Guide,
> Nielsen Norman Group 웹 가독성 연구, WCAG CJK 타이포그래피 권장사항 종합.

> **분리 구조**: 본 파일은 구조 가독성(P·H·L·C·V·CJ·BQ)만 다룬다.
> - 저자 톤(T1~T22) → [`tone.md`](./tone.md)
> - 한국어 구두점(PN1~PN6) → [`punctuation.md`](./punctuation.md)
> - AI 티 분류(A~K) → [`ai-tells.md`](./ai-tells.md)
> - 산출물 분량(LN1~LN2) → [`length.md`](./length.md)
> - 문서의 목적과 범위(PU1~PU5) → [`purpose.md`](./purpose.md)
> - 문서 유형별 적용 강도 → [`../extensions/{유형}.md`](../extensions/)

## 1. 문단 구조

### P1. 1문단 = 1아이디어

문단은 하나의 아이디어만 다룬다. 아이디어가 바뀌면 문단을 나눈다.

> **근거**: Google Developer Docs, "Each paragraph should focus on one idea."
> 독자는 문단 단위로 스캔하며, 복합 아이디어 문단은 핵심을 놓치게 한다.

Bad:
```markdown
Virtual Thread는 경량 스레드입니다. 기존 플랫폼 스레드와 달리 OS 스레드에 1:1로
매핑되지 않습니다. Spring Boot 3.2부터 설정 한 줄로 활성화할 수 있습니다.
`spring.threads.virtual.enabled=true`를 application.yml에 추가하면 됩니다.
```

Good:
```markdown
Virtual Thread는 경량 스레드입니다. 기존 플랫폼 스레드와 달리 OS 스레드에 1:1로
매핑되지 않습니다.

Spring Boot 3.2부터 설정 한 줄로 활성화할 수 있습니다.
`spring.threads.virtual.enabled=true`를 application.yml에 추가하면 됩니다.
```

### P2. 문단 길이 2-4문장

1문장은 파편화, 6문장 초과는 과밀.

> **근거**: NNG, 웹 사용자는 전체 텍스트의 20-28%만 읽는다.
> 짧은 문단이 스캔 효율을 높인다.

판단 기준:
- 1문장 문단 → P4(단문 문단) 규칙에 해당하는가? 아니면 다음 문단과 합칠 수 있는가?
- 5문장 이상 → 아이디어를 분리할 수 있는가? 뒤쪽 문장이 새로운 관점인가?

### P3. 주제문 선행

문단의 첫 문장이 핵심이다. 독자는 첫 문장 이후 건너뛸 수 있다.

> **근거**: NNG, "Users scan in an F-shaped pattern."

Bad:
```markdown
여러 방법을 시도해 보았습니다. Lettuce 커넥션 풀을 조정하고, 타임아웃을 변경하고,
캐시 TTL도 수정했습니다. 결국 문제의 원인은 DNS 해석 지연이었습니다.
```

Good:
```markdown
문제의 원인은 DNS 해석 지연이었습니다. Lettuce 커넥션 풀, 타임아웃, 캐시 TTL을
순서대로 의심했지만, 최종적으로 DNS resolve 시간이 병목이었습니다.
```

### P4. 단문 문단은 강조·전환·결론에만

1-2문장 문단이 본문 흐름 중간에 반복되면 파편화 인상을 준다.

허용되는 경우:
- 섹션 도입부 (전환)
- 핵심 결론 강조
- 인용·경고·참고 블록

### P5. 열거 vs 산문

3개 이상 나열은 목록으로, 인과·맥락 설명은 산문으로.

> **근거**: Microsoft Writing Style Guide, "Use a list for three or more items."

판단 기준:
- 항목 간 순서·인과 관계가 없다 → 비순서 목록 (`-`)
- 항목 간 순서가 있다 → 순서 목록 (`1.`)
- 항목에 설명이 필요하다 → 산문 또는 정의 목록

### P6. 코드 블록 전후에 설명 산문

코드 블록만 나열하면 "코드 없이도 글이 읽히는가?" 테스트에 실패한다.

> **근거**: Google Developer Docs, "Don't just show code; explain it."

규칙:
- 코드 블록 **앞**: 이 코드가 무엇을 하는지 (목적)
- 코드 블록 **뒤**: 결과나 주의사항 (선택적)
- 연속 코드 블록 2개 이상이면 사이에 설명 삽입

### P7. 산문 연속 제한

소제목 없이 5문단 이상 이어지지 않는다.

> **근거**: NNG, 소제목은 시각적 앵커 역할을 하며, 스캔 패턴을 안내한다.

### P8. 문단 간 전환

갑작스러운 주제 전환을 금지한다. 논리적 연결어 또는 구조적 전환(소제목)으로 맥락을 유지한다.

판단 테스트: 이전 문단 마지막 문장과 다음 문단 첫 문장을 연속으로 읽었을 때 자연스러운가?

### P9. 명사 연속 나열 제한

조사·연결어 없이 명사가 4개 이상 연속되면 조사를 넣거나 풀어 쓴다. 특히 제목·소제목에서 명사만 쌓으면 관계가 드러나지 않아 텔레그래프체로 읽힌다.

Bad:
```markdown
외부 조회 의존 제거
어뷰징 대응 로그 증적 추적
```

Good:
```markdown
외부 조회 의존을 제거
어뷰징 대응을 위한 로그 증적 추적
```

### P10. 지시어는 가리킬 대상이 앞에 있어야 한다

`이것`·`그`·`둘`·`두 문장`·`위 표` 같은 지시 표현은 가리킬 대상이 **같은 문단 또는 바로 앞 문단에 실물로** 있어야 한다. 요약 블록에만 있고 본문에 없으면 본문이 독립적으로 성립하지 않는다. 요약을 건너뛴 독자에게는 지시 대상이 없다.

Bad:
```markdown
## 왜 수치가 다를까

두 문장이 동시에 참이려면 조건이 서로 달라야 합니다.
```

Good:
```markdown
## 왜 수치가 다를까

하나는 "7~10배 빠르다" 고 하고, 다른 하나는 "차이가 없다" 고 합니다.

둘 다 맞는 말이라면 각각 맞는 조건이 서로 다른 것입니다.
```

`ai-tells.md A-6`(대명사 강박적 매핑)은 대명사를 **너무 많이** 사용하는 문제이고, 이 항목은 가리킬 것이 **없는** 문제다. 둘은 다른 결함이다.

### P11. 두 번 읽어야 뜻이 오는 표현을 남기지 않는다

관용 표현을 그 표현이 붙는 범주 밖의 대상에 사용하면 독자가 뜻을 추론해야 한다. 저자에게는 자연스럽게 읽히므로 자가 검증에서 잘 빠진다.

Bad:
```markdown
둘이 동시에 참이려면 조건이 나뉘어 있어야 합니다.
```

`갈리다`는 의견이나 길이 나뉠 때 사용하는 말이라 조건에 붙으면 뜻이 한 번에 오지 않는다.

Good:
```markdown
둘 다 맞는 말이라면 각각 맞는 조건이 서로 다른 것입니다.
```

판정 기준은 하나다. **소리 내어 읽었을 때 되돌아가면 위반이다.** `tone.md`가 확립된 관용구를 예외로 두는 것과 충돌하지 않는다. 그 예외는 대상 범주가 맞을 때에 한한다.

### P12. 단순 정보를 문장으로 늘리지 않는다

값·항목·경로처럼 그 자체가 정보인 것은 목록·표·라벨로 적는다. 서술어를 붙여 문장으로 만들면 줄당 정보량이 떨어지고, 무엇을 말하는 문장인지가 서술어에 가린다.

자리로 판정한다.

| 자리 | 위반 | 대신 |
|------|------|------|
| 목록·표의 도입 | 서술문으로 늘린다 | 라벨로 적는다 |
| API 지목 | 메서드·경로가 주어 자리에 온다 | 행위로 적고 경로는 하단 항목으로 내린다 |
| 항목 수 | 문장에 개수를 적는다 | 세지 않는다 |

Bad:
```markdown
남길 세 줄이다.

* 사용자 수별 처리량
* 최대 처리량과 평평해지는 지점
* 그 지점의 제약 지점
```

Good:
```markdown
**남길 것**

* 사용자 수별 처리량
* 최대 처리량과 평평해지는 지점
* 그 지점의 제약 지점
```

「세 줄이다」는 정보를 담지 않고, 항목이 늘거나 줄면 틀린 말이 된다.

API 를 가리킬 때는 행위가 주어다. 경로는 구체값이라 읽는 줄에서 내린다.

Bad:
```markdown
`POST /v1/reports` 하나다.
```

Good:
```markdown
보고서 생성 하나다.

**호출**

* 생성 `POST /v1/reports`
```

`tone.md T3` 과 방향이 반대다. T3 는 산문에서 서술어를 빼는 것을 막고, 이 항은 목록으로 적을 자리를 문장으로 늘리는 것을 막는다. 두 항이 만나는 지점은 목록 블록이고, 그 안에서는 T3 의 개조식 예외가 적용된다.

## 2. 헤딩 계층

### H1. 제목은 하나만

H1(`#`)은 문서당 하나. 블로그는 front matter `title`, 위키는 `subject`가 H1 역할.
본문은 H2(`##`)부터 시작한다.

### H2. 레벨 건너뛰기 금지

H2 → H4처럼 레벨을 건너뛰지 않는다. H2 → H3 → H4 순서를 지킨다.

> **근거**: WCAG 1.3.1, 스크린 리더 사용자가 헤딩 레벨로 문서 구조를 파악한다.

### H3. 빈 헤딩 금지

헤딩 아래에 최소 1문단(또는 하위 헤딩)이 있어야 한다.

### H4. 헤딩 텍스트 형태 통일

같은 레벨의 헤딩은 문법적 형태를 통일한다.

Bad:
```markdown
## 설치 방법
## 설정을 변경하기
## 테스트
```

Good (명사형):
```markdown
## 설치
## 설정
## 테스트
```

**어미와 시제도 통일 대상이다.** 같은 성격의 헤딩이 섞이면 하나만 튄다.

Bad:
```markdown
## 측정 방법
## 어떻게 선택했나      <- 형태와 시제가 둘 다 어긋난다
## 결과 비교
```

Good:
```markdown
## 측정 방법
## 선택 기준
## 결과 비교
```

질문형 헤딩은 형태 통일의 대상이 아니라 쓰지 않는 형태다. [tone.md T18](tone.md#소제목을-물음으로-달지-않는다) 이 정본이다. 이전에는 질문형 어미를 `~까?` 로 통일하라고 두었으나, 소제목을 물음으로 달지 않기로 하면서 통일할 대상이 없어졌다.

## 3. 목록과 테이블

### L1. 목록 항목 수

3-7개가 적정. 2개 이하는 산문으로, 8개 이상은 그룹화한다.

> **근거**: Miller's Law, 인지 부하 적정 범위 7±2.

### L2. 목록 항목 병렬 구조

모든 항목의 문법적 형태를 통일한다.

Bad:
```markdown
- 설정 파일을 수정합니다
- 테스트 실행
- 배포는 CI/CD로 자동 진행됩니다
```

Good:
```markdown
- 설정 파일을 수정한다
- 테스트를 실행한다
- CI/CD로 배포한다
```

### L3. 테이블 용도 제한

테이블은 비교·대조에만 사용한다. 단순 나열에는 목록이 적합하다.

### L4. 테이블 열 제한

열 5개 이하를 유지한다. 초과 시 테이블을 분할하거나 목록으로 전환한다.

> **근거**: 모바일 환경에서 5열 초과 테이블은 가로 스크롤이 발생한다.

### L5. 비교는 결론과 함께 놓는다

L3 에 따라 테이블을 비교·대조에 사용했다면, 그 비교가 무엇을 말하는지 같은 자리에서 한 문장으로 맺는다. 표만 두고 다음 절로 넘어가면 독자가 판정을 대신 해야 한다.

Bad:
```markdown
| 방안 | 비용 | 위험 |
|------|------|------|
| A | 낮음 | 높음 |
| B | 높음 | 낮음 |

## 다음 절
```

Good:
```markdown
| 방안 | 비용 | 위험 |
|------|------|------|
| A | 낮음 | 높음 |
| B | 높음 | 낮음 |

되돌릴 수 없는 작업이므로 위험을 먼저 본다. B 로 간다.

## 다음 절
```

여러 비교가 이어지는 문서는 비교 단위마다 맺는다. 마지막에 몰아서 한 번 맺으면 앞 비교들이 무엇을 위해 있었는지 읽는 동안 알 수 없다.

> **근거**: 비교를 제시하는 행위와 그 비교로 무엇을 정했는지는 별개의 정보다. 뒤를 생략하면 독자가 저자의 판단을 추측한다.

### L6. 산문이 인접한 표·목록을 되풀이하지 않는다

표 앞뒤의 산문이 표의 각 행을 풀어 쓰지 않는다. 같은 사실이 한 문서 안 두 자리에 있으면 고칠 때 한쪽만 고쳐지고, 읽는 쪽은 같은 내용을 두 번 받는다.

**표 앞 한 줄 도입은 정상이다.** 무엇을 비교하는 표인지 말하는 문장이고, 행을 옮겨 적는 것이 아니다. 판정은 「이 문단을 지우면 표에 없는 정보가 사라지는가」로 한다. 사라지지 않으면 지운다.

Bad:
```markdown
세 경로의 비용은 다음과 같습니다. A 경로는 11ms 이고, B 경로는 37ms 이며,
C 경로는 1200ms 입니다.

| 경로 | 비용 |
|------|------|
| A | 11ms |
| B | 37ms |
| C | 1200ms |
```

Good:
```markdown
세 경로의 비용입니다. C 만 다른 자릿수입니다.

| 경로 | 비용 |
|------|------|
| A | 11ms |
| B | 37ms |
| C | 1200ms |
```

정규식으로 판정하지 않는다. 도입과 되풀이는 같은 낱말을 사용하고 차이는 표에 있는 값을 옮겼는지에만 있다.

### L7. 불릿은 개조식으로 닫는다

불릿에 문장체(`~습니다`·`~했습니다`)가 섞이면 목록의 밀도가 산문과 같아진다. 목록을 쓴 이유가 사라진다.

| 불릿 형태 | 예 |
|------|-----|
| 지적된 형태 | `- 대시보드가 준비되기 전이라 임시 대체하여 배포했습니다. 선택 시 다른 패널이 보입니다` |
| 기대 형태 | `- 임시 대체 배포 — 선택 시 다른 패널 표시` |

한 불릿에 두 문장 이상을 넣지 않는다. 두 문장이 필요하면 판단이 둘이라는 신호이므로 불릿을 나눈다.

명사형 또는 종결 생략으로 닫는다. 연결어미(`~하고`·`~하게`)로 끝내면 뒤 절이 지워진 것으로 읽힌다.

**줄글과 목록의 경계**: 항목 사이에 순서·인과가 있으면 줄글로 쓴다. 목록은 나란한 항목을 나열하는 자리다. 인과를 불릿으로 끊으면 독자가 관계를 복원해야 한다.

L2(병렬 구조)와 겹치지 않는다. L2 는 항목 사이의 형태 통일을 보고 L7 은 각 항목이 개조식인지를 본다. 항목 전부가 문장체로 통일돼 있으면 L2 는 통과하고 L7 은 걸린다.

### L8. 열 이름이 담는 값을 지목하고, 적용 범위를 셀에 드러낸다

L3~L5 는 표의 용도·열 수·비교 결론을 다루고 열 자체의 설계는 다루지 않았다. 그래서 일부 행에만 해당하는 규칙이 전역 규칙으로 읽히고, 무엇이든 들어갈 수 있는 열 이름이 쓰인다.

| 판정 대상 | 판정 | 근거 |
|-----------|------|------|
| 열 이름의 구체성 | 「항목」·「이름」·「내용」처럼 무엇이든 들어갈 수 있는 이름을 사용하지 않는다. 그 열이 담는 값을 지목한다 | Microsoft Writing Style Guide, Tables · Google 기술 문서 가이드 |
| 행 식별 열의 위치 | 행을 식별하는 정보를 맨 왼쪽 열에 둔다 | 같음 · Chicago Manual of Style (stub column) |
| 적용 범위 | 행마다 적용 범위가 다르면 그 범위를 열로 드러낸다. 해당 없는 칸을 비우거나 대시로 두지 않고 「해당 없음」을 적는다 | Microsoft (빈 칸·대시 금지) |
| 열 안의 형태 통일 | 한 열의 셀은 형태를 통일한다. 명사면 전부 명사, 동사구면 전부 동사구 | Microsoft · Google · The Open Group |
| 열 이름과 셀의 관계 | 열 이름과 셀을 이어 한 문장이 되게 설계하지 않는다 | Microsoft (번역·재사용에서 깨진다) |
| 셀 분량 | 셀이 두 문장을 넘으면 표가 맞는 형식인지 다시 본다 | Google |

**적용 범위를 열로 두는 판정은 자체 판단이다.** 외부 근거가 말하는 것은 해당 없는 칸을 비우지 말라는 것까지다. 범위가 다른 행이 섞였을 때 그것을 열로 올릴지 표를 나눌지는 우리가 정한다. 표를 나누면 같은 대상을 두 자리에서 고치게 되므로 열을 택했다.

**키-값 표의 「값」 열은 대상이 아니다.** 왼쪽 열이 무엇의 값인지 이미 지목하고 있으면 오른쪽 열 이름이 그것을 반복할 필요가 없다. 설정 키와 그 설정값, 속성과 그 속성값을 나란히 두는 표가 여기 해당한다. 이 예외를 적지 않으면 훑을 때마다 같은 두 칸이 위반으로 잡히고 이름만 길어진다.

**열 이름을 명사형으로 고정하지 않는다.** 외부 근거는 「정확하고 구체적으로」까지이고 명사형을 요구하지 않는다. 구어형 열 이름(`무엇을 보나`)을 걷는 판정은 헤딩 규칙 H4 의 확장이며 그쪽 근거로 판정한다. 열 안의 형태 통일은 외부 근거가 있고 이것과 별개다.

### C2. 인라인 코드 용도 제한

인라인 코드(`` ` ``)는 변수명·파일명·명령어에만 사용한다. 강조 용도로 사용하지 않는다.

- 변수·함수: `virtualThreadEnabled`, `handleRequest()`
- 파일: `application.yml`, `build.gradle`
- 명령어: `./gradlew test`
- ~~강조~~: ~~`중요한 내용`~~ → **중요한 내용** (볼드 사용)

### C3. 긴 코드 분할

20줄 이상의 코드 블록은 핵심 부분을 분할하고 각각에 설명을 붙인다.

규칙:
- 20줄 미만: 한 블록으로 유지
- 20-40줄: 논리적 단위로 2-3개 블록 분할
- 40줄 초과: 핵심만 발췌하고 전체 코드는 링크·접기 처리

## 5. 시각적 리듬

### V1. 텍스트 밀도 균형

산문 → 목록·코드·테이블 → 산문 순으로 교대 배치한다. 같은 유형이 길게 이어지면 독자 피로를 야기한다.

Anti-pattern:
```
산문 → 산문 → 산문 → 산문 → 산문 → 코드 → 코드 → 코드
```

Good:
```
산문 → 코드 → 산문 → 테이블 → 산문 → 목록 → 산문
```

### V2. 시각적 변화 주기

스크롤 3회(약 15-20문장) 이내에 시각적 요소(목록·코드·테이블·이미지·인용)가 등장해야 한다.

### V3. TL;DR / 1분 요약

요약을 둘지는 문서 종류로 결정한다(아래 "콘텐츠 유형별 프로필"). 두는 경우 다음을 따른다.

**분량**: 1분 내 읽히게. 한국어 약 200~250어절(8~12줄), 한 화면(스크롤 없이), 본문의 5~10% 이내. 불릿 3~5개(각 1~2줄).

**구조 (BLUF)**: 결론을 맨 앞에.
1. 무엇을(What): 결론·요지 한 줄
2. 왜(Why): 해결한 문제 한 줄
3. 근거 불릿 3~5개: 결과·수치·한계

**요약 ≠ 결론 선행**: 요약은 사전지식 없이 읽히는 What/Why다. 상세 결론은 문서 성격에 따라 본문 끝에 둘 수 있다. 용어에 의존하는 요약은 위아래 왕복 독해를 부른다.

**가드**: 스크롤을 넘기거나 본문 10%를 넘으면 요약이 아니다. 불릿 5개 초과 금지.

> 근거: 성인 묵독 속도 한국어 약 202어절/분·영어 238WPM(기술 문서는 더 느림), BLUF·above-the-fold 원칙.

## 7. Blockquote 렌더링

### BQ1. Blockquote 내 문장 개행

Chirpy prompt blockquote(`.prompt-tip`, `.prompt-info`, `.prompt-warning`, `.prompt-danger`)에서
문장 종결 후 시각적 개행이 필요하면 `<br>`을 사용한다.
마크다운 blockquote는 단일 개행을 무시하므로, 의도된 개행에는 명시적 `<br>`이 필수이다.

규칙:
- 문장 종결(`~입니다`·`~습니다`) 후 아이디어가 전환되면 `<br>` 삽입
- 같은 아이디어의 부연이면 연결 유지 (개행 불필요)
- `<br>`은 종결 문장 끝에 붙이고, 다음 줄은 `>`로 시작

Bad:
```markdown
> **TL;DR** Forward Auth는 인가를 위임하는 패턴입니다.
> 파일 스트리밍 구간에 Auth가 끼지 않아 병목이 없습니다.
{: .prompt-tip }
```

Good:
```markdown
> **TL;DR** Forward Auth는 인가를 위임하는 패턴입니다.<br>
> 파일 스트리밍 구간에 Auth가 끼지 않아 병목이 없습니다.
{: .prompt-tip }
```

## 콘텐츠 유형별 프로필

요약(TL;DR) 여부는 **문서 종류(성격)**로 결정한다. 출력창(블로그·위키)은 요약을 자체 결정하지 않고 **담긴 문서 종류를 따른다**. 예외: 위키 허브 페이지(하위 목록 인덱스)는 인덱스형 문서라 자체 규칙.

유형별 V3 값은 [`extensions/profiles.md`](../extensions/profiles.md) 의 `base 대비 적용 강도` 가 정본이다. 이 파일에 유형별 표를 따로 두면 두 표가 어긋난다.

익스텐션이 없는 종류만 여기서 정한다.

| 문서 종류 | 요약 | 사유 |
|----------|------|------|
| 회고 | 조건부 | 마무리가 요약이면 생략 |

## 검증 체크리스트

자동 판별 `가능` 항목은 `../metrics/readability_count.py` 가 센다. 판정하지 않고 위치와 수치만 낸다.

```bash
python3 config/style-rules/metrics/readability_count.py README.md docs/*.md
```
