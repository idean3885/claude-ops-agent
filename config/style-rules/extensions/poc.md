# PoC 익스텐션

> **Base**: `base/readability.md` + `base/tone.md` + `base/punctuation.md` + `base/ai-tells.md`
> **Adds**: PoC 문서 특화 규칙 (다섯 단계 구조 + 독자별 요약 위치 + 재현 가능성 + 성공기준 사전정의 + 성공·실패 동시기록 + 확증편향 방지 + 후보 비교)
> **정본**: PoC 문서 구조의 정본은 이 파일이다. `skills/write` 유형 표와 `skills/infra-lab` 실험 기록은 이 구조를 링크한다.
> **Profile**: 적용 대상·base 대비 적용 강도·분량 기준값·합격선은 [profiles.md](profiles.md) 가 정본이다.

PoC 문서는 기술 검증의 결과를 "된다·안 된다"로 명확히 결론짓고, 동일 환경에서 재현 가능한 절차를 남기는 것이 목적이다.

## PC1. 요약 위치는 독자가 하는 일로 정한다

요약(TL;DR)을 둘지는 문서 종류가 아니라 **독자가 무엇을 하러 오는가**로 정한다.

| 독자가 하는 일 | 예 | 요약 |
|---|---|---|
| 「검증한다」 (근거를 따져 결정에 참여) | 팀 리뷰용 PoC, 설계 검토 | 두지 않는다. 목적 · 성공 기준이 맨 앞, 결론은 맨 끝 |
| 「가져간다」 (결론을 믿고 쓸지 판단) | 기술 공유, 상위 보고, 블로그 아티클 | 목적 앞에 둔다. |

- 같은 PoC 도 시점별로 다름: 리뷰 전에는 요약 없이, 결정 뒤 공유할 때 요약 추가
- 리뷰 문서의 결론 선행 금지: 근거를 읽지 않고 결론만 다루게 됨, 외부 사례(맥락과 범위부터 시작하는 설계 문서, 회의 시작에 전문을 묵독하는 서술형 메모)도 결론으로 시작하지 않음

요약을 둘 때는 다음 3가지를 명시한다.

- **판정**: 된다·안 된다·조건부 (한 단어)
- **핵심 수치**: 검증 결과의 핵심 지표 (응답 시간·메모리 등)
- **적용 범위·한계**: 어떤 환경에서 성립하는지

```markdown
## TL;DR

- **판정**: 조건부 (JDK 21+, Spring Boot 3.2+)
- **수치**: 동시성 1000 요청 처리, p99 240ms (기존 380ms 대비 37% 감소)
- **한계**: ThreadLocal 기반 라이브러리(MDC 등)와 충돌. 우회책 별도 PoC 예정
```

## PC2. 재현 가능성: 환경 명시

조건 단계(공통 환경)에는 동일 검증을 재현하는 데 필요한 모든 정보를 기재한다.

```markdown
## 조건

### 공통 환경

- JDK: 21.0.2 (Temurin)
- Spring Boot: 3.2.3
- 데이터베이스: PostgreSQL 16 (로컬 docker)
- 부하 도구: k6 0.49.0
- 설정: `application.yml` 전문 (코드 블록)
```

## PC3. 코드 → 결과 → 해석 순서

PoC 본문은 세 구간의 반복이다.

```markdown
### 시도 1: virtual thread 활성화만

(코드)
```yaml
spring.threads.virtual.enabled: true
```

(결과)
```
p99: 320ms
처리량: 850 req/s
```

(해석)
처리량은 개선됐지만 p99 가 충분히 떨어지지 않았습니다. 다음 변수로 ThreadLocal 사용처를 의심합니다.
```

## PC4. 결론 섹션 = 판단 근거 + 다음 단계

```markdown
## 결론

- 도입 가능 여부: 조건부 도입
- 판단 근거: TL;DR 수치 + ThreadLocal 충돌 영향 범위 추정
- 제약사항: MDC·SecurityContext 영향
- 다음 단계: ThreadLocal 우회 PoC, 메모리 프로파일링
```

## PC5. 성공 기준 사전 정의

목적 단계에 "어떤 결과가 나오면 성공인가"를 검증 시작 전에 명시한다. 측정 가능한 지표여야 한다.
검증 결과를 본 뒤에야 등장하는 성공 기준(사후 정의)은 위반이다: 결과를 역산해 기준을 끼워 맞춘 것과 구분이 안 된다.

```markdown
## 목적

- 목표: SFTP 임베드 서버가 동시 5세션을 처리할 수 있는가
- 성공 기준: 5세션 모두 Virtual Thread 에서 처리, 전부 성공
```

## PC6. 결과 = 성공 + 실패 동시 기록

검증(PC3) 섹션에 PASS 항목만 있고 실패·미수행 항목이 없으면 위반이다.
"이것은 되고, 이것은 안 되고, 이것은 아직 모른다"를 구분해 기록한다. 실패 기록은 성공 기록만큼 정보 가치가 있다: 동일한 탐색의 중복을 막는다.

```markdown
### 시도 2: ThreadLocal 캐시 제거

(결과)
성공: 캐시 제거 후 p99 190ms
실패: 배치 워커 경로는 여전히 ThreadLocal 의존, 이번 범위에서 미해결
미수행: 캐시 미스 시 fallback 경로는 부하 조건에서 미검증
```

## PC7. 가설-실험-판단 순서 (확증편향 방지)

검증 섹션은 "결론(적용한다) → 근거 나열" 순서로 쓰지 않는다. "가설 → 실험 → 결과 → 판단" 순서로 쓴다.
결론을 먼저 정하고 근거를 뒤에 배치하면, 반증할 수 있었던 결과도 확증 사례로만 읽힌다.

```markdown
[위반]
"Virtual Thread를 적용합니다" (결론)
  → 왜? I/O 바운드이므로 (근거 1)
  → 왜? 설정 한 줄이므로 (근거 2)

[준수]
가설: Virtual Thread가 동시 요청 처리 병목을 해소할 것이다
실험: 동시 1000 요청, p99 측정
결과: p99 240ms (기존 380ms 대비 37% 감소)
판단: 적용한다 (ThreadLocal 우회책은 별도 PoC)
```

## PC8. 후보 비교: 선택 기준 + 장단점 (후보가 있을 때만)

여러 후보를 검토했다면 표(또는 준하는 장표)로 "선택 기준 × 후보 × 장단점"을 드러낸다.
표만 있고 선택 사유가 없으면 K3([`knowledge.md`](knowledge.md): 정의 비교는 표보다 판단 기준)와 같은 이유로 불충분하다: 표 아래 선택 이유를 반드시 붙인다.

구조는 MADR 의 Considered Options 절을 따른다.

- **선택 기준**: 후보를 판정한 기준
- **후보**: 기각한 것을 포함한 전체 후보: 기각 근거 자체가 정보
- **후보별 장단점**: 표 형태
- **선택**: 표 아래 1~2문장으로 선택 기준 대비 최종 판단

```markdown
## 검토한 대안

| 후보 | 장점 | 단점 |
|------|------|------|
| A안 | ... | ... |
| B안 (채택) | ... | ... |

B안을 택한 이유: 선택 기준인 X 에서 A안보다 우위였고, Y 트레이드오프는 이번 범위에서 허용 가능했다.
```

후보가 하나뿐인 단순 기술 타당성 검증("만들 수 있는가?")에는 해당 없다. 실제로 후보 비교가 있었을 때만 요구한다.

## 필수 구조

다섯 단계를 이 순서로 둔다. 처음 보는 독자가 「이게 뭐지」(목적) → 「무엇과 무엇을 비교하나」(조건) → 「어떻게 쟀나」(절차) → 「무엇이 나왔나」(결과) → 「그래서」(결론) 순서로 답을 얻는다.

| 단계 | 담는 것 | 규칙 |
|------|---------|------|
| 1. 목적 | 이 문서가 답하는 질문 한 문장, 사전 성공 기준 | PC5 |
| 2. 조건 | 비교하는 조건(표: 무엇을 어디에 연결했나), 용어, 공통 환경 | PC2 · PC8 |
| 3. 절차 | 시나리오, 보는 지표와 얻는 방법, 가설 | PC7 |
| 4. 결과 | 지표, 성공 기준 대조, 성공 · 실패 · 미수행 | PC3 · PC6 |
| 5. 결론 | 판정, 근거, 제약, 다음 단계 | PC4 |

```markdown
## TL;DR (PC1: 가져가는 독자일 때만)
## 목적 (질문 한 문장 + PC5 성공 기준)
## 조건 (비교 조건 표 + 용어 + PC2 공통 환경, 후보가 있으면 PC8)
## 절차 (시나리오 + 지표와 얻는 방법 + PC7 가설)
## 결과 (PC3 코드·결과·해석, PC6 성공·실패·미수행, 성공 기준 대조)
## 결론 (PC4 판정·근거·제약·다음 단계)
```

조건 단계를 따로 두는 이유: 비교하는 두 조건이 독립 절로 없으면 조건 설명이 결과 아래 줄글로 밀려나고, 독자는 결과를 읽는 동안 무엇과 무엇을 비교하는지 모른다.
